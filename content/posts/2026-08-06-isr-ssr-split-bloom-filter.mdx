## 전량 ISR이 감당이 안 되기 시작했다

[지난 글](/posts/2026-07-04-partial-isr-cost-analysis)에서 레시피 상세페이지 전량 ISR의 비용을 뜯어봤다. 국제화로 캐싱 대상 URL이 226,116개(ko 119,500 / ja 53,328 / en 53,288)가 됐고, 크롤러 요청은 하루 약 9만 회. 캐시에 한 번 저장하는 비용이 한 번 렌더하는 비용의 4.7배라서, 배포 사이 방문이 6회를 넘는 페이지만 캐싱이 이득이라는 손익분기가 나왔다. 여기에 Vercel 청구서 밖의 비용 — 매번 렌더하면 백엔드 DB와 서버도 그만큼 더 맞는다 — 까지 얹어서, 실제 분리 기준은 방문 3~4회 선으로 잡았다.

그래서 결론은 정해져 있었다. 검색에 노출된 레시피만 ISR로 캐싱하고, 나머지는 방문할 때마다 렌더한다. 문제는 구현이다. 같은 `/recipes/:id` URL에서 어떤 레시피는 ISR로, 어떤 레시피는 SSR로 — 이걸 Next.js에서 어떻게 분리해야할까?

## 시도 1 — 렌더 도중에 connection()으로 갈아타기

첫 설계는 지난 글에 쓴 그대로였다. 백엔드가 레시피마다 매일 매겨주는 `isIndexed` 값을 상세 데이터 body로 받고, `false`면 렌더 도중 `connection()`을 호출한다. `connection()`이 한 번이라도 불린 렌더는 결과를 캐시에 저장하지 않는 동적 렌더로 처리되니, 데이터를 먼저 받아 보고 조건부로 부르면 페이지별 분기가 된다 — 는 계산이었다.

로컬에서는 잘 동작했다. 배포하니 비색인 레시피 상세가 전부 500을 뱉었다.

원인은 같은 라우트에 있던 `generateStaticParams`였다. 인기 레시피 목록을 빌드 때 미리 렌더해두는 함수인데, 이게 있으면 Next는 라우트를 정적 우선으로 취급한다. 정적 우선 라우트에서 프리렌더 목록 밖의 레시피가 첫 런타임 요청을 받으면, 렌더 도중의 `connection()` 호출이 `DYNAMIC_SERVER_USAGE` 에러를 던진다. 정적으로 만들기로 한 페이지를 렌더하다 말고 동적으로 바꾸려 한 셈이라, Next가 모순으로 판정하고 렌더를 터뜨린 것이다.

## 시도 2 — generateStaticParams를 빼면 되지 않을까

충돌의 원인이 `generateStaticParams`니, 그걸 제거했다. 이제 모든 레시피가 요청 시점에 렌더되고, `isIndexed`가 true면 캐시되는 ISR, false면 `connection()`으로 동적 렌더 — 가 될 줄 알았다.

실제로는 `generateStaticParams`가 사라지자 라우트 전체가 요청마다 동적으로 렌더됐다. ISR로 캐시되는 쪽이 아예 없어진 것이다. 이 상태에서 `connection()` 분기는 렌더 모드를 바꾸는 스위치가 아니라, 이미 동적인 렌더 위에서 데이터 캐시 동작만 갈라놓는 죽은 스위치였다. 결국 분기를 전부 걷어내고 모든 레시피를 일반 SSR로 서빙하는 상태로 후퇴했다. 분리는커녕 ISR 이득 자체가 사라졌다.

두 실패는 방향이 반대다. 시도 1은 정적 쪽에 서서 동적으로 못 넘어갔고, 시도 2는 동적 쪽에 서서 정적으로 못 돌아왔다. **라우트가 정적이냐 동적이냐는 렌더가 시작되기 전에 정해지고, 렌더 도중에는 못 바꾼다.** `connection()`은 정해진 모드 안에서 저장 여부를 조정하는 도구지, 페이지별로 모드를 오가게 해주는 도구가 아니었다. 분기하려면 렌더가 시작되기 전, 요청이 라우트에 도착하기 전에 갈라야 한다고 생각했다.

## 시도 3 — 미들웨어에서 라우트를 갈라버리기

요청이 라우트에 닿기 전에 개입할 수 있는 지점은 미들웨어다. 그래서 라우트를 물리적으로 두 개로 쪼갰다. (`/recipes/:id`는 ISR 트랙, `/recipes/dyn/:id`는 `force-dynamic` 트랙) 렌더 본체는 공유하고, 미들웨어가 색인된 레시피면 그대로 통과시키고 아니면 dyn 트랙으로 rewrite한다.

redirect가 아니라 rewrite인 게 중요하다. redirect는 브라우저에게 "다른 URL로 다시 요청해라"라고 응답하는 것이고, rewrite는 URL을 그대로 둔 채 내부적으로 다른 경로의 결과를 서빙하는 것이다. 사용자와 크롤러가 보는 주소는 끝까지 `/recipes/:id` 하나다.

```ts
const resolveRecipeTrack = async (id: string): Promise<"isr" | "dynamic"> => {
  try {
    const bloom = await get<Bloom>("indexedBloom");
    if (bloom && bloomHas(bloom, id)) return "isr";
  } catch {
    // Edge Config unavailable → safe dynamic
  }
  return "dynamic";
};
```

판정 실패나 데이터 부재는 전부 동적 트랙으로 보낸다. 동적 렌더는 "저장 비용을 안 낸다"는 쪽이라 잘못 가도 페이지가 깨지지 않고, 덕분에 Edge Config를 세팅하기 전에도 배포할 수 있었다.

남은 문제가 이 글의 후반부다. 미들웨어는 모든 요청마다 실행되는데, 미들웨어 단에서 어떻게 레시피ID만 보고 인덱스 여부를 파악할 수 있을까? 답은 이미 예시 코드에서 스포가 섞여있다.

## 미들웨어가 색인 여부를 어떻게 아는가 — 네트워크 왕복 없이

색인된 레시피 ID 목록은 어딘가에 있어야 한다. 후보는 S3든 DB든 많지만, 미들웨어에서 요청마다 외부 저장소를 조회하면 모든 페이지 응답에 그 왕복 시간이 얹힌다. 크롤러가 하루 최대 9만 번 두드리는 사이트에서 그 비용을 낼 수는 없었다. **미들웨어 분기의 관건은 판정 데이터를 네트워크 왕복 없이 읽는 것이고, 선택지는 번들에 굽거나 엣지에 복제해두는 두 갈래뿐이다.**

번들에 포함하는 방법 — ID 목록을 코드에 포함해 배포하는 방식 — 은 읽기가 순수 메모리 접근이라 가장 빠르다. 대신 값이 배포 아티팩트에 묶여서, 매일 갱신되는 색인 목록을 반영하려면 매일 배포해야 한다.

Edge Config는 그 묶임을 푼 물건이다. 값을 Vercel이 엣지 노드에 미리 복제해둬서 미들웨어에서의 읽기는 로컬이고, 갱신은 배포와 무관하게 API로 PATCH한다. 실제로 일일 cron이 배포 없이 매일 값을 갈아끼우고, 반대로 배포를 해도 값은 유지된다. 읽기는 번들처럼, 쓰기는 배포와 독립적으로 — 정확히 이 용도에 맞는 조합이라 이걸 골랐다.

공짜는 아니었다. Edge Config는 값 하나의 크기 제한이 64KB다. 색인된 레시피 ID는 수만 개다. ID 하나가 8자니 문자열 그대로는 300KB를 넘어, 64KB엔 어림도 없다.

## bloom filter — 64KB에 3.8만 개 넣기

그래서 "ID 목록을 저장한다"를 포기하고 "ID가 목록에 있는지만 판정할 수 있는 요약본을 저장한다"로 문제를 바꿨다. bloom filter가 정확히 이 일을 하는 자료구조다.

원리는 비트 배열 하나와 해시 함수 k개다. ID를 등록할 때 k개 해시가 가리키는 비트들을 1로 세우고, 조회할 때 그 비트들을 다시 본다. 하나라도 0이면 그 ID는 확실히 없다. 전부 1이면 "있다" — 인데, 다른 ID들이 세워둔 비트에 우연히 다 걸렸을 가능성이 있어서 이 판정은 확률적이다. 없는 걸 있다고 하는 오탐(false positive)은 나지만, 있는 걸 없다고 하는 일은 구조적으로 없다.

이 비대칭이 우리 상황과 정확히 맞물린다. **오탐은 비색인 레시피가 ISR 트랙에 타는 방향 — 캐시 저장 비용을 조금 낭비하는 안전한 방향 — 으로만 나고, 색인된 레시피가 동적 트랙으로 새는 일은 일어날 수 없다.** 게다가 오탐률은 비트 배열 크기와 맞바꾸는 파라미터라서, 용량 한도에 맞춰 직접 고를 수 있다.

구현은 의존성 없는 유틸 하나다. FNV-1a 이중 해싱으로 k개 인덱스를 만들고, 비트셋을 base64로 직렬화해 Edge Config에 넣는다. 일일 cron이 사이트맵 API에서 색인 대상 ID를 다 받아 seed ID와 합친 뒤, 오탐률 후보 [0.1%, 0.2%, 0.5%, 1%, 2%]를 낮은 쪽부터 시도해 62KB(한도에서 여유를 뺀 값) 안에 들어가는 첫 번째를 채택한다.

지금 프로덕션 기준 수치는 이렇다. 등록 ID 37,650개(사이트맵 37,601 + 고트래픽 seed 5,243, 중복 제거), 오탐률 0.5%는 69,244바이트로 한도를 넘어 1%가 선택됐고, 결과물은 60,192바이트 — 비트 360,878개, 해시 7개다. 첫 집계 때 ko 120,256개 중 21,828개(18%)였던 색인 목록이 한 달 새 3.8만까지 자란 걸 60KB가 그대로 받아내고 있다.

오탐의 실비용도 기대값으로 가늠할 수 있다. 크롤러가 비색인 URL을 한 번씩 훑는다고 보면 그중 1%가 오탐으로 ISR 트랙에 탄다. ko 비색인 약 8.2만 페이지 기준 800여 페이지 — 전량 ISR로 되돌아가는 것에 비하면 소음 수준이다.

## 남은 이야기 — 프론트가 이 값을 들고 있는 게 맞나

글을 쓰다 보니 더 앞단의 질문이 남는다. 색인 여부는 백엔드가 매일 계산하는 값인데, 왜 프론트가 그 사본을 bloom으로 압축해 들고 다니는가. 백엔드가 레시피 ID를 발급할 때부터 색인 표식을 ID 자체에 인코딩해주면, 미들웨어는 ID 문자열만 보고 판정할 수 있고 프론트의 판별 데이터는 통째로 사라진다. 다만 ID 체계를 바꾸는 백엔드 구조 변경이라, bloom 방식의 한계가 실제로 드러날 때 다시 논의하기로 했다.

## 배운 점

라우트의 렌더 모드는 렌더 도중에 못 바꾼다. `connection()` 문서만 보면 "호출하면 동적이 된다"까지만 읽히는데, 그 호출이 라우트의 정적/동적 결정과 충돌하면 어떻게 되는지는 프로덕션 500으로 배웠다. 페이지별로 모드를 갈라야 한다면 결정 지점을 렌더 앞으로 — 미들웨어로 — 끌어내는 게 맞다.

플랫폼 제약이 자료구조를 고르게 했다. bloom filter를 쓰고 싶어서 쓴 게 아니라, "요청마다 왕복 불가"가 Edge Config를 고르게 했고 "64KB"가 bloom을 고르게 했다. 제약을 먼저 확정하면 선택지는 알아서 좁아진다.

오탐이 있는 판정도 방향이 안전하면 쓸 수 있다. 틀렸을 때 비용이 한쪽 방향으로만, 감당 가능한 크기로만 새게 설계돼 있으면 확률적 자료구조는 정확한 목록의 값싼 대체재가 된다. 반대로 오탐이 "색인 페이지가 캐시를 잃는" 방향이었다면 bloom은 처음부터 후보가 아니었다.
