## 전량 ISR 유지 비용을 줄여야 했어요

[지난 글](/posts/2026-07-04-partial-isr-cost-analysis)에서 레시피 상세 페이지 전체를 ISR로 유지할 때 발생하는 비용을 정리해 봤어요. 서비스에 국제화를 적용하면서 캐싱 대상 URL이 총 226,116개(ko 119,500개, ja 53,328개, en 53,288개)로 늘어났고, 크롤러 요청도 하루 약 9만 회 수준에 달했어요. 캐시에 페이지를 한 번 저장하는 비용이 한 번 렌더링하는 비용의 4.7배에 달하다 보니, 배포 주기 사이에 방문이 6회를 넘는 페이지만 캐싱하는 편이 손익분기점에 부합한다는 계산이 나왔어요. 여기에 매번 동적으로 렌더링할 때 백엔드 DB와 애플리케이션 서버가 받는 부하까지 함께 감안해서, 실제 캐싱 분리 기준은 방문 3~4회 선으로 잡았어요.

결론은 검색에 실제 노출된 레시피만 ISR로 캐싱하고, 나머지 레시피는 방문할 때마다 새로 렌더링하는 쪽으로 정리됐어요. 관건은 구현 방법이었어요. 동일한 `/recipes/:id` 주소 체계 안에서 어떤 레시피는 ISR로 서빙하고 어떤 레시피는 SSR로 서빙하는 구조를 Next.js에서 어떻게 풀어내야 할지 고민이 시작됐어요.

## 렌더링 도중 connection()을 호출했을 때 마주한 500 에러

첫 번째 설계는 지난 글에서 구상했던 방식 그대로였어요. 백엔드가 매일 레시피마다 갱신해 주는 `isIndexed` 플래그를 상세 데이터 본문으로 전달받고, 이 값이 `false`일 때 렌더링 도중 `connection()`을 호출하도록 작성했어요. `connection()`이 렌더링 과정에서 한 번이라도 실행되면 해당 결과가 캐시에 저장되지 않고 동적 렌더링으로 처리되니까, 응답 데이터를 확인한 뒤 조건부로 호출하면 페이지별 렌더링 분기가 가능할 것이라 판단했어요.

로컬 환경에서는 이 코드가 문제없이 동작했어요. 그런데 실제 환경에 배포하자마자 색인되지 않은 레시피 상세 페이지에서 전부 500 에러가 발생했어요.

원인은 동일한 라우트 파일 안에 작성해 둔 `generateStaticParams` 함수였어요. 인기 레시피 목록을 빌드 시점에 미리 만들어두려고 선언한 함수였는데, 이 함수가 라우트에 존재하면 Next.js는 해당 라우트 자체를 정적 우선으로 취급해요. 정적 우선으로 지정된 라우트에서 사전 렌더링 목록에 포함되지 않은 레시피가 런타임에 첫 요청을 받으면, 렌더링 과정에서 호출된 `connection()`이 `DYNAMIC_SERVER_USAGE` 에러를 던져요. 정적 페이지로 처리하기로 정의된 라우트 안에서 렌더링 중간에 동적 처리로 전환을 시도하다 보니, 프레임워크 수준에서 모순으로 판정하고 렌더링을 중단시킨 상황이었어요.

## generateStaticParams 제거 후 발생한 전체 동적 렌더링 문제

충돌을 일으킨 직접적인 원인이 `generateStaticParams`였기 때문에 이 함수를 라우트에서 제거해 봤어요. 사전 빌드 단계를 없애면 모든 레시피가 요청 시점에 렌더링을 시작하고, `isIndexed`가 true인 페이지는 ISR 캐시로 들어가고 false인 페이지만 `connection()`을 거쳐 동적으로 렌더링될 것이라 기대했어요.

하지만 실제 동작은 예상과 달랐어요. `generateStaticParams`를 제거하자 라우트 전체가 매 요청마다 동적으로 렌더링되는 상태로 전환됐어요. 결과적으로 ISR 캐시를 타는 경로가 아예 사라졌어요. 라우트 전체가 이미 동적 렌더링으로 돌아가는 환경에서는 `connection()` 분기가 렌더링 모드를 전환하는 역할을 하지 못하고, 데이터 캐시 동작만 일부 갈라놓는 무의미한 코드가 되어 버렸어요. 결국 이 분기 처리를 모두 걷어내고 모든 레시피를 일반 SSR로 서빙하도록 롤백해야 했어요. 페이지별 분기는커녕 ISR을 통해 얻으려 했던 캐싱 이점마저 사라진 셈이에요.

첫 번째 시도는 정적 라우트 설정에 묶여 동적 렌더링으로 전환하지 못했고, 두 번째 시도는 라우트가 동적으로 고정되어 정적 캐싱 상태를 살려내지 못했어요. 라우트의 기본 렌더링 모드는 컴포넌트 렌더링이 시작되기 전에 결정되며, 렌더링이 진행 중인 상태에서는 이를 동적으로 바꿀 수 없다는 점을 확인했어요. `connection()`은 이미 결정된 렌더링 모드 안에서 캐시 저장 방식을 제어하는 도구일 뿐, 요청마다 페이지 모드 자체를 교체해 주는 도구가 아니었어요. 따라서 모드를 분기하려면 요청이 라우트 렌더링 단계로 넘어가기 전, 더 앞단에서 주소를 갈라주어야 했어요.

## 미들웨어 rewrite를 활용한 ISR과 동적 트랙 분리

요청이 실제 라우트에 도달하기 전에 개입할 수 있는 위치는 미들웨어예요. 그래서 라우트를 물리적인 두 개 경로로 분리했어요. ISR을 적용할 `/recipes/:id` 트랙과, `force-dynamic`을 적용할 `/recipes/dyn/:id` 트랙을 각각 구성했어요. 화면을 렌더링하는 본체 코드는 두 경로가 공유하고, 미들웨어에서 색인된 레시피 요청은 원래 경로로 통과시키며 비색인 레시피 요청은 dyn 트랙으로 rewrite하도록 구성했어요.

사용자 경험을 해치지 않으려면 redirect가 아니라 rewrite를 사용해야 해요. redirect는 브라우저를 향해 다른 URL로 다시 접속하라고 응답을 돌려주는 방식이지만, rewrite는 사용자가 머무는 URL을 그대로 유지한 채 서버 내부적으로 다른 경로의 실행 결과를 전달해 줘요. 이 방식을 적용하면 사용자와 크롤러가 바라보는 주소는 항상 `/recipes/:id` 하나로 유지돼요.

```ts
const resolveRecipeTrack = async (id: string): Promise<"isr" | "dynamic"> => {
  try {
    const bloom = await get<Bloom>("indexedBloom");
    if (bloom && bloomHas(bloom, id)) return "isr";
  } catch {
    // Edge Config unavailable → safe dynamic
  }
  return "dynamic";
};
```

판정 과정에서 에러가 발생하거나 데이터가 누락되었을 때는 모두 동적 트랙으로 보내도록 예외 처리를 구성했어요. 동적 렌더링은 페이지 캐시 저장 비용을 추가로 발생시키지 않는 안전한 경로이기 때문에, 혹시라도 경로 판정에 실패하더라도 화면이 깨지는 장애로 이어지지 않아요. 덕분에 초기 설정 단계에서 Edge Config 데이터가 완전히 준비되기 전에도 안전하게 배포를 진행할 수 있었어요.

다만 이 구조를 실제로 운영하려면 다음 과제를 해결해야 했어요. 미들웨어는 서비스로 인입되는 모든 요청마다 매번 실행되는데, 외부 요청 없이 레시피 ID 문자열만 보고 색인 여부를 즉시 판단할 방법이 필요했어요.

## 네트워크 왕복을 없애기 위한 Edge Config 도입

색인 대상 레시피 ID 목록은 어떤 형태로든 저장되어 있어야 해요. S3나 데이터베이스 같은 외부 저장소를 둘 수도 있지만, 미들웨어 안에서 매 요청마다 외부 저장소를 조회하면 모든 상세 페이지 응답 시간에 네트워크 지연 시간이 고스란히 더해져요. 크롤러가 하루 최대 9만 번까지 페이지를 요청하는 상황에서 매번 네트워크 I/O를 발생시키는 구성은 적합하지 않았어요. 미들웨어 분기를 정상적으로 운영하려면 판정 데이터를 네트워크 왕복 없이 즉시 읽어올 수 있어야 했고, 고려할 수 있는 방식은 빌드 번들에 직접 포함하거나 엣지 저장소에 복제해 두는 것뿐이었어요.

ID 목록을 코드 번들에 직접 포함해서 배포하면 메모리에서 곧바로 읽어올 수 있어 처리 속도가 가장 빨라요. 하지만 데이터가 배포 결과물에 묶이기 때문에, 백엔드에서 매일 갱신되는 색인 목록을 반영하려면 프론트엔드 애플리케이션도 매일 새로 빌드하고 배포해야 하는 제약이 생겨요.

Edge Config는 이 종속 문제를 해결해 주는 도구였어요. 데이터를 Vercel 엣지 노드 전반에 미리 복제해 두기 때문에 미들웨어에서는 로컬 메모리에 준하는 속도로 값을 읽을 수 있고, 데이터 갱신은 별도의 배포 작업 없이 PATCH API 호출로 처리할 수 있어요. 실제로 서비스에서는 일일 cron 작업을 통해 배포 없이 매일 색인 데이터를 교체하고 있으며, 신규 코드가 배포되더라도 Edge Config에 저장된 값은 그대로 유지돼요. 번들 직접 참조처럼 빠른 읽기 속도를 확보하면서도 배포 주기와 데이터 관리를 완전히 분리할 수 있는 방식이라 이 설정을 채택했어요.

하지만 여기에도 용량 제한이라는 기술적 제약이 있었어요. Edge Config는 단일 항목의 크기가 64KB로 제한돼요. 현재 서비스에서 색인된 레시피 ID는 수만 개에 달하는데, 8자리 문자열 식별자를 원본 배열 그대로 저장하면 전체 용량이 300KB를 넘어가서 64KB 한도에 들어가지 못했어요.

## bloom filter를 적용해 64KB 안에 3.8만 개 식별자 압축하기

단순히 전체 ID 목록을 원형 그대로 저장하는 방식 대신, 특정 ID가 색인 목록에 포함되어 있는지만 빠르게 검증할 수 있는 요약 자료구조를 저장하는 방식으로 설계를 전환했어요. bloom filter가 바로 이런 요구 조건을 충족하는 자료구조예요.

bloom filter는 비트 배열 하나와 k개의 독립적인 해시 함수를 사용해 동작해요. ID를 등록할 때는 k개의 해시 함수가 계산한 각 비트 위치의 값을 1로 변경하고, 특정 ID가 포함되어 있는지 조회할 때는 해당 비트들이 모두 1로 켜져 있는지 확인해요. 비트 중 하나라도 0으로 남아 있다면 그 ID는 목록에 확실히 들어있지 않은 상태예요. 반대로 모든 비트가 1로 채워져 있다면 목록에 존재한다고 판단할 수 있어요. 다만 다른 ID들이 기록되면서 우연히 해당 비트들이 모두 1로 채워졌을 가능성이 남아 있어 판정 결과에 확률적인 오차가 존재해요. 즉, 실제로는 없는 ID를 등록되어 있다고 잘못 판단하는 오탐(false positive)은 발생할 수 있지만, 실제로 등록된 ID를 없다고 잘못 판정하는 미탐은 수학적으로 절대 발생하지 않아요.

이 오탐의 단방향성이 현재 인프라 구조와 정확하게 맞아떨어졌어요. 오탐이 발생하더라도 색인되지 않은 레시피가 ISR 트랙을 타면서 캐시 저장 비용이 약간 발생하는 선에서 그칠 뿐이고, 이미 색인된 레시피가 동적 트랙으로 잘못 빠져 캐시 혜택을 잃어버리는 상황은 구조적으로 방지돼요. 게다가 오탐률은 비트 배열의 크기와 해시 함수 개수를 조정해 조절할 수 있는 수치이기 때문에, 인프라의 64KB 용량 제한에 맞춰 직접 오탐 허용치를 조정할 수 있었어요.

구현 단계에서는 외부 라이브러리 의존성 없이 유틸리티로 작성했어요. FNV-1a 기반 이중 해싱을 사용해 k개의 비트 인덱스를 도출하고, 완성된 비트 배열을 base64 문자열로 직렬화하여 Edge Config에 저장하도록 구성했어요. 매일 실행되는 일일 cron이 사이트맵 API로부터 색인 대상 ID 전체를 받아오고 이를 고트래픽 seed ID와 병합한 뒤, [0.1%, 0.2%, 0.5%, 1%, 2%] 오탐률 후보군을 순차적으로 대입하면서 62KB(한도 용량에서 안전 여유분을 뺀 기준) 안에 들어오는 첫 번째 파라미터를 자동으로 채택해요.

현재 운영 환경에서 집계되는 세부 수치는 다음과 같아요. 중복을 제거한 등록 ID는 총 37,650개(사이트맵 37,601개 + 고트래픽 seed 5,243개)예요. 오탐률 0.5%를 적용했을 때는 직렬화 크기가 69,244바이트로 한도를 초과하여 1% 오탐률이 최종 채택되었어요. 그 결과 생성된 데이터 크기는 60,192바이트이며, 비트 수는 360,878개, 해시 함수는 7개를 사용하고 있어요. 초기 집계 당시 한국어 레시피 120,256개 중 21,828개(18%) 수준이었던 색인 목록이 한 달 사이 3.8만 개까지 늘어났지만, 여전히 60KB 안쪽에서 문제없이 관리되고 있어요.

오탐으로 인해 발생하는 실제 운영 비용도 계산해 볼 수 있어요. 크롤러가 비색인 레시피 URL을 한 번씩 순회한다고 가정하면, 전체 비색인 대상 중 1%가 오탐에 의해 ISR 트랙으로 유입돼요. 한국어 비색인 레시피 약 8.2만 개를 기준으로 환산하면 약 800여 개 페이지만 캐시 생성을 거치게 되며, 이는 전체 페이지를 ISR로 운영할 때 들던 비용과 비교하면 충분히 감당할 수 있는 수준이에요.

## 프론트엔드의 판별 데이터 유지에 관한 구조적 고민

글을 쓰다 보니 한 단계 더 근본적인 아키텍처 관점의 의문이 남았어요. 색인 대상 여부는 백엔드 시스템에서 매일 계산하고 관리하는 값인데, 프론트엔드가 이 데이터의 사본을 bloom filter 형태로 압축해 보관하고 직접 판별하는 흐름이 최선인가에 대한 점이에요. 만약 백엔드에서 레시피 ID를 처음 생성하는 시점부터 색인 여부를 식별할 수 있는 식별 체계를 ID 자체에 포함해 준다면, 미들웨어는 별도의 요약본 없이 ID 문자열만으로 라우팅 모드를 즉시 분기할 수 있고 프론트엔드의 데이터 저장소도 완전히 걷어낼 수 있어요. 다만 이 작업은 백엔드 전반의 ID 발급 및 데이터 모델을 변경해야 하는 구조적 작업이기 때문에, 현재 운영 중인 bloom filter 방식의 한계가 실제로 드러나는 시점에 다시 검토하기로 정리했어요.

## 문제를 해결하며 확인한 기술적 기준들

라우트 컴포넌트 내부에서 렌더링이 이미 시작된 이후에는 렌더링 모드를 임의로 변경할 수 없어요. `connection()` 공식 문서의 동작 설명만 보고 단순히 함수 호출을 통해 동적 렌더링으로 전환할 수 있을 것이라 기대했지만, 라우트 자체의 정적 모드 판정과 충돌할 때 500 에러로 이어진다는 점을 운영 환경을 통해 확인했어요. 페이지 단위로 렌더링 방식을 다르게 가져가려면 컴포넌트 렌더링 이전 단계인 미들웨어에서 진입 경로 자체를 분리해야 해요.

인프라가 가진 물리적 제약은 적합한 자료구조를 결정하는 명확한 기준이 되었어요. 단순히 특정 자료구조를 도입하려 했던 것이 아니라, 미들웨어 내부에서 외부 네트워크 통신을 배제해야 한다는 조건이 Edge Config를 선택하게 만들었고, 64KB라는 단일 용량 제한이 bloom filter를 적용하게 만든 계기가 되었어요. 시스템의 구체적인 제약 조건을 먼저 정의하면 구현 방식은 자연스럽게 좁혀져요.

확률에 기반한 자료구조라 하더라도 오탐이 미치는 영향이 서비스 관점에서 안전한 방향으로만 흐른다면 충분히 실무에 적용할 수 있어요. 판정이 빗나갔을 때 발생하는 부작용이 캐시 용량을 일부 추가 소비하는 수준으로 통제되어 있었기 때문에 bloom filter를 정확한 데이터 목록의 안정적인 대체재로 채택할 수 있었어요. 만약 반대로 오탐이 발생했을 때 색인된 페이지가 캐시 대상에서 제외되는 구조였다면 이 방식은 선택하기 어려웠을 거예요.
