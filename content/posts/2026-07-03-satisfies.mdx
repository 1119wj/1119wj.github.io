AI시대에 맞게 기본기를 다시 다져보며 `satisfies`라는 걸 다시 접했습니다. 저희 코드에서는 평소에 잘 보이지 않는 녀석이라.. 매번 흐린눈으로 넘어갔었는데요. 이번 글은 `satisfies`의 올바른 사용, 리팩토링 기대효과에 대해서 다룹니다.

`satisfies`를 뒤늦게 제대로 이해하고 나니, 코드베이스에 있는 `Record<...>` 상수들이 죄다 눈에 밟히기 시작했습니다. 이걸 전부 satisfies로 바꾸면 타입이 더 좁아지고 안전해지지 않을까 싶었습니다. 그래서 바꾸기 전에 먼저 세어봤습니다. 어노테이션이 붙은 객체·배열 리터럴 상수가 프로젝트 전체에 100곳 남짓 있었습니다.


그래서 `satisfies`에서 어려운 부분은 "이득인가, 손해인가"를 가려내는 일입니다. 이 글은 그 구분선을 어디에 긋는지에 대한 이야기입니다.

### satisfies가 뭐길래 — 어노테이션·as와 나란히 놓고 보기

객체 리터럴에 타입을 붙이는 방법은 세 가지입니다. 같은 객체 하나에 셋을 나란히 대보면 차이가 분명해집니다.

```ts
type Keys = "a" | "b" | "c" | "d";

// 1) 어노테이션
const p1: Record<Keys, unknown> = { a: 0, b: "hello" };
//    p1.a 의 타입은 unknown. a 가 number 였다는 사실이 사라집니다.

// 2) as 단언
const p2 = { a: 0, b: "hello" } as Record<Keys, unknown>;
//    검사를 건너뜁니다. 틀린 타입을 우겨넣어도 통과합니다.

// 3) satisfies
const p3 = { a: 0, b: "hello", x: 8 } satisfies Record<Keys, unknown>;
//    x 는 Keys 에 없으므로 에러. 검사는 하되,
//    p3.a 는 number, p3.b 는 string 으로 좁게 유지됩니다.
```

어노테이션은 객체가 타입을 만족하는지 검사해주는 대신, 변수의 타입을 그 어노테이션으로 고정합니다. `p1`의 타입은 `Record<Keys, unknown>`이 되고, `a`가 number였다는 좁은 정보는 버려집니다. `as`는 반대로 검사 자체를 건너뜁니다. 컴파일러에게 "그냥 이 타입이라고 치자"고 단언하는 거라, 틀린 단언도 막지 못합니다.

`satisfies`는 이 둘의 가운데입니다. 어노테이션처럼 조건을 검사하되, 변수의 실제 타입은 리터럴에서 추론한 좁은 형태로 그대로 둡니다. `p3.a`는 `unknown`이 아니라 `number`로 남고, `x`처럼 조건에 없는 키는 그 자리에서 걸립니다. "이 객체가 T의 모양을 갖추긴 했는지 확인은 하고 싶지만, 타입은 내가 쓴 그대로 좁게 쓰고 싶다" — 그럴 때 쓰는 게 `satisfies`입니다.

여기에 `as const` 하나를 더 세워야 이 글의 나머지가 안 샙니다. 위 예시의 `as`는 "이 타입이라고 치자"는 단언이지만, `as const`는 리터럴을 아예 읽기 전용(readonly)의 가장 좁은 타입으로 굳히는 다른 도구입니다. 뒤에 나올 최종 코드와 `DISH_TYPE_CODES`에 이 `as const`가 등장하니, 네 도구가 아니라 세 도구를 한 줄로 정리하고 갑니다.

| 도구 | 검사 | 변수 타입 |
| --- | --- | --- |
| 어노테이션 `: T` | O | `T`로 넓힘 (키 정보 손실) |
| `as const` | X | 좁힘 + readonly |
| `satisfies T` | O | 추론된 좁은 타입 유지 |

`as const`와 `satisfies`는 둘 다 "좁게 유지"라 자주 뭉뚱그려지지만, 결정적으로 갈리는 건 **검사 열**입니다. `as const`는 조건을 검사하지 않고, `satisfies`는 검사합니다. 이 한 칸 차이가 뒤에서 승부를 가릅니다.

### 어노테이션은 타입을 "검사"하는 대신 "넓힙니다"

문제는 이 "넓힘"이 조용히 사고를 만든다는 점입니다. 제 프로젝트에는 이런 상수가 있었습니다.

```ts
// src/shared/config/constants/recipe.ts
export const INGREDIENT_CATEGORY_CODES: Record<string, string> = {
  전체: "",
  고기: "meat",
  채소: "vegetable",
  // ... 한글 카테고리 키 13개
};
```

`Record<string, string>`은 "아무 문자열 키나 받고 값은 string"이라는 뜻입니다. 이 어노테이션을 붙이는 순간, TypeScript는 이 객체에 실제로 어떤 13개 키가 들어있는지를 잊습니다. 그래서 `keyof typeof INGREDIENT_CATEGORY_CODES`를 물어보면, 실제 키 13개가 아니라 **`string | number`가 돌아옵니다.**

이게 왜 문제인지는 소비처에서 드러납니다.

```ts
// src/entities/ingredient/model/api.ts
category: category
  ? INGREDIENT_CATEGORY_CODES[
      category as keyof typeof INGREDIENT_CATEGORY_CODES
    ]
  : null,
```

여기서 `category`는 `string | null`입니다. `as keyof typeof INGREDIENT_CATEGORY_CODES`는 방금 봤듯 `keyof`가 `string | number`이므로, 사실상 `category as string`입니다. 

이 캐스트는 유효한 카테고리 키로 좁혀주는 타입 가드처럼 생겼지만, 실제로는 아무것도 하지 않습니다. `"고기류"` 같은 오타를 넣어도, `"asdf"`를 넣어도 컴파일러는 통과시킵니다.

넓어진 타입이 위험한 이유가 여기 있습니다. 넓힘은 상수 한 줄에서 일어나는데, 그 값을 받아 쓰는 소비처는 전부 넓은 타입을 물려받습니다. 값이 실제로 쓰이는 지점(네트워크 요청)까지 거리가 멀수록, 잘못된 값은 더 늦게 드러납니다. 정작 타입 시스템은 첫 줄에서 손을 놓은 뒤입니다.

### 고치면 뭐가 좋아지나 — 그래서 실제로 바꿔봤습니다

어노테이션을 떼고, config를 union의 단일 원천으로 만들었습니다.

```ts
export const INGREDIENT_CATEGORIES = ["전체", ...INGREDIENT_CATEGORIES_BASE] as const;
export type IngredientCategoryName = (typeof INGREDIENT_CATEGORIES)[number];

export const INGREDIENT_CATEGORY_CODES = {
  전체: "",
  고기: "meat",
  // ...
} satisfies Record<IngredientCategoryName, string>;
```

이러면 `keyof typeof INGREDIENT_CATEGORY_CODES`가 실제 13개 키의 union(`"전체" | "고기" | ... | "기타"`)이 됩니다. 소비처의 `as keyof typeof` 캐스트가 그제야 진짜 의미를 갖고, `IngredientCategoryName`을 뽑아 상태·핸들러·api 경계까지 재사용합니다.

여기서 공을 정확히 나눠야 합니다. 키 union을 되살린 1차 동력은 `satisfies`가 아니라 **어노테이션을 뗀 것**입니다. `: Record<string, string>`가 `keyof`를 `string | number`로 뭉개고 있었으니, 그 어노테이션을 지우는 순간 리터럴에서 추론된 13개 키가 되살아납니다. `satisfies`가 하는 일은 그 자리에 "모양 검사"를 다시 채워 넣는 것뿐입니다 — 어노테이션이 검사와 넓힘을 한 몸으로 묶어 팔던 걸, 검사(`satisfies`)와 좁은 추론(어노테이션 제거)으로 분리한 셈입니다. 그래서 `satisfies` 없이 어노테이션만 지워도 앞의 두 버그는 똑같이 컴파일 에러로 드러납니다. `satisfies`의 몫은 그 다음, 아래에서 따로 이야기합니다.

타입을 끝까지 꿰자, 넓은 `string`이 덮고 있던 진짜 버그 두 개가 컴파일 에러로 튀어나왔습니다. 하나는 레시피 생성 화면의 "나의 재료" 탭입니다. 이건 음식 카테고리가 아니라 "내 냉장고" 필터인데, 그동안 카테고리인 척 코드맵을 타고 흘러 `undefined`가 되고 있었습니다.

다른 하나는 그 "나의 재료" 판별을 로케일별 사전 문자열(`"My Ingredients"`)로 비교하고 있어서, 한국어가 아닌 언어에서는 "내 재료" 필터가 아예 켜지지 않던 것이었습니다. 둘 다 넓은 타입이 가려주던 버그였고, 타입을 좁히자마자 드러났습니다.

그리고 여기서부터가 `satisfies`만의 몫입니다. 어노테이션 제거가 키 union을 되살렸다면, `satisfies Record<IngredientCategoryName, string>`는 코드맵이 카테고리 13개를 **빠짐없이** 덮도록 강제합니다. 나중에 카테고리를 추가하고 코드 매핑을 빠뜨리면 그 자리에서 컴파일 에러가 납니다.

이건 `as const`로는 못 하는 일입니다. "그럼 어노테이션 떼고 `as const`만 붙이면 되잖아?"의 답이 여기 있습니다. `as const`는 검사를 안 하니, 13개 중 하나를 빠뜨린 12개짜리 맵도 그냥 12개짜리 좁은 타입으로 통과시킵니다. 대상 타입(`Record<IngredientCategoryName, string>`)과 대조해 "누락"을 잡아주는 건 검사를 하는 `satisfies`뿐입니다. 런타임 가드로도 못 잡는 지점이고요.

### 함정: satisfies가 오히려 깨는 곳 — 판별 기준

문제는 나머지 상수들입니다. `Record<string, V>` 어노테이션을 `satisfies`로 바꾸면 index signature가 사라집니다. `[k: string]`이라는 "아무 문자열로나 인덱싱해도 된다"는 약속이 없어지고, 대신 구체적인 키만 가진 객체가 됩니다. 그러면 임의의 문자열 변수로 인덱싱하던 코드가 전부 타입 에러가 납니다.

```ts
// value 가 string 이라, index signature 가 없으면 인덱싱 불가
DISH_TYPE_ICONS[value];
DAY_UNIT[locale];
COOKING_METHOD_ICON[trimmed];
REFERRAL_ERROR_MESSAGES[code];
```

이런 맵들은 애초에 임의 입력을 받아 룩업하는 용도라, `[k: string]` 약속이 있어야 동작합니다. satisfies로 좁히는 건 이득이 아니라 회귀입니다.

넓은 타입이 아예 의도인 경우도 있습니다. `NOTIFICATION_STATUSES`와 `PLATFORMS`는 `readonly string[]`인데, `.includes(p.status)`처럼 임의의 문자열 인자를 받아 검사합니다. 여기에 `as const`로 좁은 튜플을 만들면, `.includes`가 그 튜플에 없는 문자열을 거부해서 오히려 컴파일이 깨집니다. 깨뜨리는 건 `as const`(좁은 튜플)이지 `satisfies`가 아닙니다 — `satisfies readonly string[]`은 타입을 안 좁히고 검사만 하므로 여기선 무해합니다. 다만 이미 넓은 게 정답인 자리라 굳이 붙일 이유도 없습니다.

그래서 판별 기준은 하나로 정리됩니다. **좁은 키 집합이 실제로 소비되면 `satisfies`가 이득이고, 임의의 문자열로 인덱싱한다면 index signature가 필요하므로 `satisfies`는 방해입니다.** 표로 옮기면 이렇습니다.

| 그 상수를 이렇게 쓰고 있다면 | satisfies |
| --- | --- |
| `keyof typeof`로 키 union을 뽑아 쓴다 | 이득 |
| 리터럴 키로 접근하되 값 타입은 안 쓴다 (`X.고기`) | 이득 없음 |
| 값을 리터럴 타입 그대로 소비한다 | 이득 (`as const satisfies`) |
| 임의의 string 변수로 인덱싱한다 (`X[key]`) | 깨짐 — index signature 필요 |
| 배열을 map / iterate만 한다 | 이득 없음 |

### 팀 차원 재발 방지 — 정답은 이미 우리 파일 안에 있었습니다

올바른 패턴은 문제의 상수 바로 옆에 이미 있었습니다. 같은 `recipe.ts` 파일입니다.

```ts
// 정답: 어노테이션 없이 as const
export const DISH_TYPE_CODES = {
  전체: null,
  볶음: "FRYING",
  // ...
} as const;

export type DishType = keyof typeof DISH_TYPE_CODES; // 실제 키 union

// 바로 아래: 어노테이션이 as const 를 죽인 코드
export const DISH_TYPE_ICONS: Record<string, string> = {
  전체: "all.webp",
  // ...
} as const;
```

`DISH_TYPE_CODES`는 어노테이션을 안 붙였기 때문에 `keyof typeof`가 실제 키 union이 되고, `DishType`이 좁은 타입으로 제대로 뽑힙니다. 반면 바로 아래 `DISH_TYPE_ICONS`는 `as const`를 붙여놓고도 앞에 `Record<string, string>` 어노테이션이 있어서, 그 `as const`가 아무 일도 못 합니다. 정확히는 `as const`가 리터럴을 좁게 추론하긴 하는데, 어노테이션이 변수 타입을 다시 `Record<string, string>`으로 넓혀 그 좁은 결과를 덮어써 버립니다. 좁히려고 붙인 `as const`의 산출물이 곧바로 버려져 죽은 코드로 남는 겁니다.

여기서 팀 규칙 하나가 나옵니다. **맵 상수를 새로 만들 때 `: Record<...>` 어노테이션을 붙이지 말고 `as const`나 `satisfies`로 선언하고, 키 타입이 필요하면 `keyof typeof`로 파생합니다.** 어노테이션은 타입을 명시했으니 안전하다는 느낌을 주지만, 정작 키 정보를 지우는 게 그 어노테이션입니다.

코드 리뷰에서 볼 체크포인트도 단순합니다. `: Record<string, ...> = {`로 시작하는 리터럴 상수가 보이면, 그 키를 `keyof typeof`로 쓰는 곳이 있는지 확인합니다. 있으면 그 `keyof`는 지금 `string`으로 새고 있으니 `satisfies` 후보입니다. 없고 임의 문자열로 인덱싱만 한다면 어노테이션이 맞습니다.

### 마치며

이번엔 TS의 `satisfies`에 대해서 알아보면서 해당 기능을 통해 좁은 타입의 이점을 어떻게 살리면 좋을지에 대해 알아봤습니다. 추가로 어노테이션과 `as const`가 경합할 때 `as const`가 죽은 코드가 된다는 사실도 새롭게 배웠습니다.
