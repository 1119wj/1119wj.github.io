## 22.6만 개 URL 전체를 캐싱하면서 마주한 비용 문제

저희 서비스의 레시피 상세 페이지는 전부 Next.js의 ISR(증분 정적 재생성) 방식으로 캐싱하고 있어요. ISR은 페이지를 처음 렌더링할 때 생성된 결과물(HTML)을 캐시에 저장해 두고, 다음 방문부터는 서버에서 다시 렌더링하지 않고 미리 저장해 둔 정적 파일을 그대로 반환하는 방식이에요. 서비스 초기 레시피가 5만 개 안팎이었을 때는 이 구성만으로도 충분히 빠르고 효율적이었어요.

하지만 서비스에 다국어(i18n) 지원이 들어가면서 상황이 크게 달라졌어요. 기존 한국어(`ko`) 페이지에 일본어(`ja`)와 영어(`en`) 로케일이 추가되면서, 캐싱 대상이 되는 전체 URL 수가 순식간에 급증했거든요.

| 로케일 | URL |
| --- | --- |
| ko | 119,500 |
| ja | 53,328 |
| en | 53,288 |
| 합계 | 226,116 |

여기서 ISR의 구조적인 약점이 드러났어요. **프론트엔드 코드를 한 번 새로 배포하면, 기존에 저장소에 쌓여 있던 렌더링 캐시가 전부 무효화된다는 점이에요.** 새 배포는 완전히 비어 있는 캐시 상태에서 시작하거든요.

문제는 배포 직후에 찾아와요. 구글·네이버·빙 같은 검색 크롤러들이 사이트맵을 따라 수많은 페이지를 다시 훑기 시작하는데요. 캐시가 완전히 비어 있다 보니 크롤러가 들어올 때마다 페이지를 매번 처음부터 새로 렌더링하고, 그 결과물을 다시 캐시 저장소에 새로 기록하게 돼요. 바로 이 "캐시 새로 저장(Write)"이 계속해서 비용을 발생시키는 주원인이었어요. 크롤러가 보내는 요청만 해도 하루에 대략 9만 회에 달하거든요.

특히 이 구조에서 가장 비효율을 키우는 건 롱테일 페이지들이에요. 전체 22.6만 개 URL 중 대다수는 검색 결과에 노출된 적도, 실제 사용자가 클릭해 본 적도 거의 없는 비인기 페이지들이에요. 하지만 사이트맵에 주소가 올라와 있다는 이유만으로 크롤러는 성실하게 페이지를 방문하죠. 결국 아무도 읽지 않는 페이지를 비싼 연산 비용을 들여 렌더링하고 저장소에 기록하는 셈인데요. 정작 저장 비용만 계속 나가고, 그 비용을 상쇄해 줄 실제 사용자 방문(= 캐시 읽기)은 거의 일어나지 않는 상태였어요.

## 검색 노출 실적이 있는 페이지만 골라 캐싱하기로 결정한 과정

그래서 모든 페이지를 무조건 캐싱하지 않기로 했어요. 검색 엔진에 노출된 실적이 있는 페이지만 ISR로 캐싱해 두고, 노출 실적이 없는 나머지 롱테일 페이지는 요청이 들어올 때마다 서버에서 그때그때 렌더링(SSR)하고 캐시 저장소에는 남기지 않는 방식으로 분리했어요.

판단 기준은 백엔드에서 매일 배치로 레시피마다 "검색 노출 실적 있음"(`isIndexed`) 플래그를 내려주도록 구성했어요.

- `isIndexed = true`: 검색 노출 실적이 있으므로 지금처럼 ISR 캐시를 유지해요.
- `isIndexed = false`: 렌더링 도중에 Next.js의 `connection()`을 호출해서, 해당 페이지가 캐시 저장소에 저장되지 않도록 강제로 동적 렌더링 모드로 전환해요.
- 값이 내려오지 않는 경우(`undefined`): 기존 방식대로 캐싱을 적용해 안전한 쪽(`true`)으로 처리해요.

여기서 중요한 점이 있어요. 상세 페이지 내부에서 레시피 데이터를 가져오는 fetch 자체는 계속 캐시 설정을 유지한다는 사실이에요. 덕분에 페이지 단위로는 매번 렌더링하더라도 원본 데이터는 이미 저장된 캐시를 활용하기 때문에, 백엔드 API 서버로 매번 요청이 전달되지는 않아요. 결과적으로 백엔드 부하는 늘어나지 않아요.

Next.js에서 페이지를 캐싱하지 않게 만들 때, 보통 파일 상단에 `export const dynamic = 'force-dynamic'` 같은 설정을 선언하곤 하잖아요? 하지만 이 방식은 파일 전체 단위로 고정되기 때문에, 레시피 데이터의 조건에 따라 유연하게 켜고 끌 수가 없어요.

반면 렌더링 도중에 실행되는 `connection()` 함수를 쓰면 이 문제를 깔끔하게 해결할 수 있어요. 렌더링 과정에서 이 함수가 단 한 번이라도 호출되면, Next.js는 해당 페이지를 "캐시에 저장하지 않는 페이지"로 인식하거든요. 덕분에 백엔드 데이터를 먼저 받아와 `isIndexed` 값을 확인한 뒤 조건부로 `connection()`을 호출해도 아무런 문제가 없어요. Next.js의 캐시 저장은 컴포넌트 렌더링이 완전히 끝난 뒤에 이뤄지기 때문에, "캐시가 먼저 저장되어 버려서 동적 전환을 못 막는" 상황 자체가 일어나지 않기 때문이에요.

참고로 노출 여부 데이터를 구글 서치콘솔 API에서 직접 긁어오는 방식도 검토해 봤어요. 하지만 해당 API의 일일 조회 한도가 2천 URL 수준으로 제한되어 있어서, 22.6만 개나 되는 URL을 매번 확인하려면 100일 넘게 걸린다는 계산이 나왔어요. 그래서 서치콘솔 API 대신 실제 유입된 클릭 및 노출 실적 데이터를 판단 기준으로 채택했어요. 한국어(`ko`) 레시피 120,256개를 대상으로 첫 집계를 돌려보니, 실제로 노출 실적이 있는 레시피는 21,828개(약 18%)에 불과했어요.

## 인프라 과금 단가 기준 (Seoul 리전, 2026-07-04 확인)

비용을 계산하기 위해 당시 서울 리전 기준으로 확인한 Vercel의 인프라 단가는 다음과 같아요.

| 리소스 | 단가 |
| --- | --- |
| 캐시 저장(ISR Write) | $5.20 / 100만 단위 (1단위 = 8KB) |
| 캐시 읽기(ISR Read) | $0.52 / 100만 단위 |
| 함수 호출 | $0.60 / 100만 |
| CPU 실행 | $0.169 / 시간 |
| 메모리 | $0.0140 / GB·시간 |

Vercel의 캐시 아키텍처는 크게 두 단계로 나뉘어 있어요. 사용자와 가까운 엣지에 위치한 임시 캐시(CDN) 레이어와, 그 뒤편에서 영구 보관을 담당하는 실제 캐시 저장소 레이어로 분리되어 있죠.

여기서 핵심은 **앞단의 임시 캐시(CDN)를 읽고 쓰는 작업은 무료이고, 뒤쪽에 있는 실제 캐시 저장소에 데이터를 쓰거나 읽어올 때만 과금된다는 점이에요.** 다시 말해, 이미 캐시가 정상적으로 올라간 페이지를 반복해서 사용자에게 응답하는 과정은 대부분 공짜예요. 비용은 처음 렌더링을 마친 뒤 실제 저장소에 기록할 때(Write), 그리고 CDN에 데이터가 없어서 실제 저장소까지 내려가 데이터를 가져올 때(Read)만 발생해요.

또한 페이지 내용에 변경이 없다면 백그라운드 캐시 갱신이 일어나도 저장소에 새로 기록하지 않아요. 결국 우리가 마주하는 대량의 캐시 저장 비용은, 대부분 새 배포가 진행되면서 기존 캐시가 비워질 때 집중적으로 발생하고 있던 거예요.

## 캐시 저장 1회와 렌더링 1회의 비용 비교

저장 비용을 구체적으로 따져보기 위해, 실제 프로덕션에 배포된 레시피 상세 페이지 3개를 표본으로 잡아 결과물 크기를 측정해 봤어요. 원본 HTML 크기는 383~530KB, 압축 전송 크기는 53~61KB였고, 여기에 함께 딸려오는 데이터(RSC 페이로드)의 원본 크기는 약 251KB였어요. 이 결과물들이 압축되어 Vercel의 실제 캐시 저장소에 들어갈 때의 크기는 대략 96KB로 잡았어요. Vercel은 캐시 저장량을 8KB 단위로 올림 계산하므로, 96KB는 딱 12단위에 해당해요.

이제 **매 방문마다 서버에서 새로 렌더링할 때의 비용(`C_render`)**을 계산해 볼게요. 평균 사양을 CPU 200ms, 메모리 1.75GB 할당, 총 소요 시간 500ms로 가정했어요.

| 항목 | 계산 | 비용 |
| --- | --- | --- |
| 함수 호출 | $0.60/100만 | $0.00000060 |
| CPU 실행 | (0.200/3600) × $0.169 | $0.00000939 |
| 메모리 | (1.75 × 0.500/3600) × $0.0140 | $0.00000340 |
| 합계 | | $0.00001339 |

반면 **한 번 캐시 저장소에 기록하는 비용(`W`)**은 다음과 같아요.
- `W` = 12단위 × ($5.20 / 100만) = $0.0000624

숫자를 비교해 보면 **캐시에 딱 한 번 저장하는 비용이, 서버에서 함수를 실행해 페이지를 렌더링하는 1회 비용보다 4.7배나 비싸요.**

이 말은 곧, 페이지를 비싼 돈 들여 캐싱해 두는 선택이 경제적이려면, 그 비싼 저장 비용을 이후에 발생하는 수많은 (거의 무료에 가까운) 캐시 읽기 요청으로 충분히 회수할 수 있어야 한다는 뜻이에요. 만약 배포 주기 동안 페이지 조회 수가 얼마 나오지 않는다면, 캐싱하는 행위 자체가 오히려 손해인 셈이죠.

## 캐싱이 유리해지는 손익분기 방문 횟수 계산

한 번 배포된 뒤 다음 배포가 이뤄지기 전까지, 한 페이지에 총 `V`번의 방문 요청이 들어온다고 가정해 볼게요.

- 캐싱 적용(ISR): 첫 방문 시 1회 렌더링 후 캐시 저장소에 기록하고, 이후 방문은 저장된 캐시로 무료 서빙해요 → `C_render + W`
- 매번 렌더링(SSR): 방문이 들어올 때마다 매번 새로 렌더링해요 → `V × C_render`

이때 매번 새로 렌더링하는 쪽이 캐싱하는 것보다 더 저렴해지는 조건식은 다음과 같이 정리할 수 있어요.

```
V × C_render < C_render + W
V < 1 + W / C_render
```

여기에 앞서 구한 비용 수치를 대입해 보면 손익분기 방문 수 `V*`가 나와요.
`V* = 1 + 62.4/13.39 ≈ 6`

즉, **배포와 배포 사이에 해당 페이지를 찾는 방문 횟수가 6번 미만이라면 매번 렌더링하는 편이 더 싸고, 6번 이상 방문이 발생해야 캐싱해 두는 쪽이 이득이에요.**

페이지의 저장 용량과 렌더링 CPU 소요 시간에 따라 손익분기점이 어떻게 달라지는지도 표로 정리해 봤어요.

| 저장 크기 | 렌더 CPU | `W` | `V*` |
| --- | --- | --- | --- |
| 64KB (8단위) | 200ms | $0.0000416 | 4.1 |
| 96KB (12단위) | 200ms | $0.0000624 | 5.7 |
| 128KB (16단위) | 200ms | $0.0000832 | 7.2 |
| 96KB (12단위) | 120ms | $0.0000624 | 8.0 |
| 96KB (12단위) | 350ms | $0.0000624 | 3.8 |

그렇다면 우리 서비스의 롱테일 페이지들은 배포 사이에 과연 몇 번이나 방문될까요?

전체 크롤링 요청 수가 하루 9만 건인데요. 이 중 실제 페이지 렌더링을 유발하는 요청을 넉넉하게 절반(하루 4.5만 건)으로 잡더라도, 전체 22.6만 개 URL로 나눠보면 개별 페이지는 평균적으로 5일에 딱 한 번 크롤링되는 꼴이에요. 만약 서비스 배포 주기가 3일이라면, 배포와 배포 사이에 한 페이지가 방문되는 횟수는 겨우 0.6회에 불과해요. 손익분기 기준인 6회에는 한참 못 미치는 수치죠.

따라서 트래픽이 거의 없는 롱테일 페이지는 캐시를 저장하지 않고 매번 렌더링하는 편이 훨씬 경제적이에요. 반대로 클릭 실적이 잡히는 인기 페이지들은 실제 사용자의 유입에 크롤러 방문까지 더해져 손익분기인 6회를 아주 쉽게 넘기기 때문에, 기존처럼 캐싱을 유지하는 게 확실히 이득이에요.

## 예상되는 비용 절감액과 오분류 위험 요소

**기대되는 절감 효과 (저장 비용 제거):**
롱테일 페이지는 어차피 배포 주기 동안 들어오는 방문이 사실상 1회 수준에 불과해요. 그렇기 때문에 이 페이지들을 동적 렌더링으로 전환하더라도, 기존에 ISR 첫 진입 시 발생하던 "초기 1회 렌더링"을 그대로 대체할 뿐 추가적인 렌더링 부하나 비용이 더 생기지 않아요. 즉, 페이지를 캐시 저장소에 쓰면서 발생하던 비용 `W`를 고스란히 아낄 수 있는 구조예요.

한 달 동안 롱테일 페이지에서 아낄 수 있는 캐시 저장 횟수는 대략 `90,000 × f × 30 × 0.82` 공식으로 계산해 볼 수 있어요. (여기서 `f`는 하루 9만 건의 요청 중 실제 페이지 렌더링을 유발하는 요청의 비율이고, `0.82`는 노출 실적이 없는 롱테일 페이지의 비율이에요.)

| `f` | 페이지/일 | 월 저장 횟수 | 월 절감 |
| --- | --- | --- | --- |
| 0.3 | 2.7만 | ~66만 | ~$41 |
| 0.5 | 4.5만 | ~111만 | ~$69 |
| 0.7 | 6.3만 | ~155만 | ~$97 |

단순히 캐시 저장 비용만 따져보아도 매월 $40~100 정도를 바로 줄일 수 있어요. 여기에 계산에 포함하지 않은 함수 서빙 비용(불필요한 실행 시간 및 데이터 전송량), 그리고 배포할 때마다 롱테일 페이지들을 전부 다시 렌더링하고 캐시 저장소에 다시 밀어 넣던 오버헤드가 통째로 사라지는 효과까지 감안하면 실제 체감 절감액은 이보다 훨씬 더 클 것으로 보여요.

**잠재적인 위험 비용 (노출 여부 오분류 시):**
만약 실제로는 방문이 자주 발생하는 인기 페이지인데 `isIndexed=false`로 잘못 분류되어 동적 렌더링으로 넘어간다면 어떻게 될까요? 캐싱해 두었더라면 무료로 응답했을 요청마다 매번 $0.0000134의 렌더링 비용이 발생하게 돼요. 앞서 확인한 손익분기점(방문 6회)을 넘어서는 페이지가 비캐싱 대상으로 잘못 분류되면 오히려 캐싱할 때보다 손해가 생기는 셈이죠.

하지만 다행히도 `isIndexed` 플래그의 특성 덕분에 이런 손해를 자연스럽게 방어할 수 있어요. 검색 엔진에서 한 번이라도 노출이나 클릭 실적이 잡히면 이 플래그는 `true`로 올라가고, 이후에 다시 `false`로 떨어지지 않도록 설계되어 있거든요. 따라서 갑자기 검색 유입이 늘어나기 시작한 롱테일 페이지가 있더라도, 다음 날 배치가 돌고 나면 자동으로 캐싱 대상 그룹으로 승격되어 안전하게 보호돼요.

## 실제 측정 데이터로 보정해야 할 부분

위에서 도출한 계산 모델을 실무 환경에 맞춰 더 정밀하게 다듬으려면 두 가지 지표를 실제 데이터로 보정해 주어야 해요.

1. 현재 Vercel 대시보드에 표시되는 캐시 저장(ISR Writes) 수치는 그대로 신뢰하기 어려워요. 얼마 전 레시피를 22만 개로 한꺼번에 채웠는데요. 이때 발생한 일회성 대량 저장 기록이 섞여 있어서 평소의 평균 지표가 과도하게 부풀려져 있거든요. 이 일회성 스파이크가 완전히 가라앉은 뒤 정상화된 추이를 지켜볼 필요가 있어요.
2. 9만 건의 크롤링 요청 중 실제 페이지 렌더링을 유발하는 요청 비율 `f`, 그리고 레시피 페이지 1개당 발생하는 실제 캐시 저장 단위 수를 정확하게 측정하면 절감 예상 범위를 하나의 확실한 숫자로 좁힐 수 있어요.
   - 요청 비율 `f`는 서버 및 CDN 로그를 바탕으로 전체 요청 중 `/recipes/*` 경로에 정상적인 페이지 응답을 보낸 비율을 집계해 산출할 수 있어요.
   - 페이지당 저장 단위 수는 대시보드에 집계된 월간 총 저장 단위 수를 실제 저장된 페이지 수로 나누어 계산할 수 있어요.

이렇게 평상시 상태의 월간 저장 단위 수를 실측해 낸 뒤 여기에 ($5.20 / 100만)을 곱해주면, 부분 ISR 전환을 통해 우리가 얻을 수 있는 저장 비용 절감의 상한선을 정확하게 도출할 수 있을 거예요.
