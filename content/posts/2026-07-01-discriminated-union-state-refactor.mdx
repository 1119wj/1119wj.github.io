### 판별 유니온이란 무엇인가요?

판별 유니온은 공통 판별자 필드(`kind`, `type`, `status` 같은 리터럴 값) 하나로 여러 갈래를 구분하는 타입이에요. 각 갈래는 자기만의 필드를 갖고, 판별자로 분기하면 그 갈래의 데이터만 좁혀져 안전하게 접근할 수 있어요. "이 상태일 때만 이 데이터가 있다"를 타입 수준에서 못 박아서, 말이 안 되는 조합을 애초에 만들 수 없게 돕는 유용한 패턴이에요.

판별 유니온 개념을 다시 복습한 김에, 레시피오 코드베이스에 판별 유니온이 적용되지 않은 안티패턴이 남아 있는지 찬찬히 훑어봤어요. 그러다 큐레이션 생성 도구의 `Workspace` 컴포넌트가 눈에 걸렸어요. 로딩 여부, 생성 결과, 에러 메시지가 각각 별도의 `useState`로 흩어져 있었고, 생성 버튼을 누를 때마다 이 세 상태를 손으로 맞춰 리셋하고 있었거든요.

지금 코드는 매번 세 값을 올바른 순서로 비워주는 식이라, 사람이 실수하기 딱 좋은 구조였어요.

## 판별 유니온이 불가능한 상태를 막아주는 원리

상호배타적인 상태를 boolean 여러 개로 들고 있으면, 타입 시스템은 현실에서 불가능한 조합까지 문법적으로 허용해 버려요.

```ts
type State = {
  isLoading: boolean;
  data: Recipe[] | null;
  error: string | null;
};
```

예를 들어, 이 타입은 `isLoading`이 참이면서 `data`와 `error`가 동시에 채워진 값을 전혀 막지 못해요. "로딩 중인데 결과 데이터도 있고 에러 메시지도 있다"는 기괴한 상태가 문법적으로는 합법이 되는 셈이에요.

실제로 화면에서 가능한 상태는 로딩, 성공, 에러 세 가지뿐인데, 타입은 여덟 가지 조합을 모두 열어두고 있어요. 그 격차만큼 불필요한 방어 코드가 덕지덕지 붙고, "로딩은 끝났는데 플래그를 미처 끄지 못한 상황" 같은 버그가 언제든 터질 수 있어요.

판별 유니온(discriminated union)은 공통 판별자 필드 하나로 갈래를 나누고, 각 갈래가 자기 데이터만 갖도록 깔끔하게 정리해 줘요.

```ts
type State =
  | { status: "loading" }
  | { status: "success"; data: Recipe[] }
  | { status: "error"; message: string };
```

이제 `data`는 `success`에만 있고, `message`는 `error`에만 존재해요. "로딩 상태인데 결과 데이터가 있다"는 값은 아예 타입 시스템상에서 만들 수 없어요. 불가능한 상태를 표현조차 불가능하게 만드는 것, 이 한 문장이 판별 유니온의 핵심이에요.

## 우리 코드베이스에서 이미 쓰고 있던 판별 유니온

사실 판별 유니온은 그리 낯선 패턴이 아니에요. 네이티브 앱과 웹뷰가 서로 주고받는 메시지 타입에서도 이미 판별 유니온을 잘 활용하고 있었거든요.

```ts
export type AppToWebMessage =
  | { type: "NOTIFICATION_STATUS"; payload: { status: NotificationStatus } }
  | { type: "AUTH_DIAG"; payload: AuthDiagBridgePayload }
  | { type: "KEYBOARD_STATE"; payload: KeyboardStatePayload }
  | { type: "APP_CONTEXT"; payload: AppContextPayload };
```

여기서는 판별자 필드 이름이 `status`가 아니라 `type`으로 되어 있어요. 이름은 달라도 역할은 완전히 같아요(`kind`, `type`, `status` 등 무엇이든 가능해요). `type`에 따라 `payload`의 구조가 달라지고, 각 갈래는 자기 타입에만 존재하는 필드를 갖게 돼요. 예를 들어 키보드 높이를 나타내는 `height`는 `KEYBOARD_STATE`에만 있고, 실행 환경인 `platform`은 `APP_CONTEXT`에만 들어 있어요.

```ts
function handle(msg: AppToWebMessage) {
  if (msg.type === "KEYBOARD_STATE") {
    msg.payload.height; // KeyboardStatePayload로 좁혀져 접근 가능
  }
  if (msg.type === "APP_CONTEXT") {
    msg.payload.platform; // 접근 가능
    msg.payload.height; // APP_CONTEXT엔 height가 없어 컴파일이 막음
  }
}
```

키보드 메시지인데 엉뚱하게 `platform`을 읽으려 하거나, 앱 컨텍스트 메시지인데 `height`를 읽으려는 프로토콜 위반은 컴파일 단계에서 바로 걸러져요. 네이티브에서 건너온 메시지를 `type`으로 분기하는 순간, 컴파일러가 그 갈래에 맞는 payload 모양을 확실하게 좁혀주기 때문이에요.

## 흩어진 useState로 상태를 다룰 때 생기는 문제

한 컴포넌트 안에 `useState<... | null>(null)`이 여러 개 몰려 있고, 그 바로 옆에 boolean 로딩 플래그가 나란히 놓여 있는 형태가 있어요. 저희 큐레이션을 생성하는 `Workspace` 컴포넌트가 정확히 이런 모습이었어요.

```ts
const [loading, setLoading] = useState(false);
const [localResult, setLocalResult] = useState<GenerateCurationOutput | null>(null);
const [error, setError] = useState<string | null>(null);

const onGenerate = async () => {
  setLoading(true);
  setError(null);
  setLocalResult(null);
  try {
    const r = await generateCurationViaApi({ ... });
    setLocalResult(r);
  } catch (e) {
    setError(toMessage(e));
  } finally {
    setLoading(false);
  }
};
```

코드를 한 줄씩 뜯어보면 당장 동작 자체는 문제없이 돌아가요. AI에게 아무런 제약 조건을 주지 않고 코드를 작성하게 두면 정말 흔하게 마주치는 형태이기도 해요.

하지만 여기서 가장 큰 문제는 한 번 생성 작업을 돌릴 때마다 세 개의 setter를 일일이 건드려야 한다는 점이에요. 시작할 때 셋을 한꺼번에 리셋하고, 성공하면 결과를 채우고, 실패하면 에러를 채운 뒤, `finally`에서 로딩을 꺼줘야 해요. 이 순서나 과정 중 하나라도 어긋나면 화면 상태는 바로 꼬여버려요.

만약 `setLocalResult(null)` 같은 초기화 코드를 빠뜨리거나 호출 순서가 뒤바뀌면, 우리가 원치 않는 엉뚱한 동작이 나타날 수 있어요. 지금은 세 줄이 제자리에 딱 맞춰 들어가 있어서 괜찮아 보이지만, 실은 그 '괜찮음'을 타입 시스템이 아니라 개발자의 주의력에 의존해 아슬아슬하게 지키고 있었던 거예요.

## 리팩토링할 대상과 그대로 둘 대상 구분하기

그렇다고 해서 flat하게 나열된 boolean이 보인다고 무작정 다 뜯어고칠 필요는 없어요. 같은 코드베이스 안에 있는 `useImageLoader` 역시 `isLoading`, `isLoaded`, `hasError`라는 세 개의 boolean을 반환하고 있거든요. 하지만 이 세 값은 독립된 `useState`로 흩어져 있는 게 아니라, 단 하나의 `status`에서 파생된 계산값에 불과해요.

```ts
// 이해를 돕기 위한 예시
const [status, setStatus] = useState<"loading" | "loaded" | "error">("loading");
return {
  isLoading: status === "loading",
  isLoaded: status === "loaded",
  hasError: status === "error",
};
```

진실의 원천(Source of Truth)이 `status` 하나로 모여 있기 때문에, `isLoading`과 `hasError`가 동시에 참이 되는 말도 안 되는 상태는 구조적으로 절대 나올 수 없어요.

결국 반환값이나 상태에 boolean이 몇 개 있느냐가 핵심이 아니라, 그 boolean들의 출처가 하나인지 아니면 여러 개로 나뉘어 있는지가 판단 기준이에요.

그래서 코드 스멜을 판단할 수 있는 기준 질문을 두 가지로 정리해 봤어요.

1. 각 상태가 자기만의 데이터를 따로 들고 있는가?
2. 그리고 한 번 상태가 전이될 때 여러 setter를 동시에 건드려야 하는가?

앞서 본 `useImageLoader`는 로딩, 성공, 에러 상태에 딸린 추가 데이터가 없고 상태 전이도 `setStatus` 한 번으로 끝나니 둘 다 '아니오'에 해당해요.

반면 `Workspace`는 성공 상태일 때 결과를 들고 있고 에러 상태일 때 메시지를 들고 있으며, 상태가 바뀔 때마다 세 개의 setter를 동시에 맞춰줘야 하니 둘 다 '예'에 해당해요. 우리가 손봐야 할 곳은 바로 이런 후자의 경우예요.

## 상태 성격에 맞게 판별 유니온 구조 선택하기

판별 유니온을 상태에 적용하는 방법은 크게 두 가지가 있어요. 하나는 상태 전체를 판별 유니온 객체 하나로 묶어서 단일 `useState`에 담는 방식이고(형태 A), 다른 하나는 앞서 본 `useImageLoader`처럼 `status` 문자열만 판별자로 두고 나머지 값은 별도 `useState`로 관리하는 방식이에요(형태 B). 둘 다 판별 유니온을 활용하는 접근이 맞지만, 어느 쪽을 골라야 할지는 각 상태가 데이터를 직접 들고 다니는지에 따라 갈려요.

`Workspace`의 성공 상태는 생성 결과를 들고 있어야 하고, 에러 상태는 에러 메시지를 품고 있어야 해요. 만약 이걸 형태 B로 처리해 버리면, 결과와 메시지가 `status` 옆에서 여전히 독립된 `useState`로 둥둥 떠다니게 되고, 결국 똑같은 동기화 문제를 다시 마주하게 돼요.

`useImageLoader`는 로딩, 성공, 에러 상태에 붙는 별도 데이터가 없었기 때문에 형태 B로도 충분했지만, `Workspace`는 각 kind마다 필요한 데이터가 제각각이라 형태 A가 반드시 필요했어요.

그래서 `Workspace`를 아래처럼 깔끔하게 고쳐봤어요. 각 `status`마다 필요한 데이터 타입을 명확히 정의하고, 하나의 state 안에서 안전하게 관리하도록 바꾼 거예요.

```ts
type GenerationState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; result: GenerateCurationOutput }
  | { status: "error"; message: string };

const [generation, setGeneration] = useState<GenerationState>({ status: "idle" });
```

이렇게 타입을 정의해 두면, 새로운 `onGenerate` 함수는 상태 객체를 통째로 한 번만 교체하는 형태로 단순해져요.

```ts
const onGenerate = async () => {
  if (!selected) return;
  setGeneration({ status: "loading" });
  try {
    const r = await generateCurationViaApi({ ... });
    setGeneration({ status: "success", result: r });
  } catch (e) {
    setGeneration({ status: "error", message: toMessage(e) });
  }
};
```

시작 지점에 덕지덕지 붙어 있던 세 줄짜리 리셋 코드가 완전히 사라졌어요. `loading` 상태로 전이되는 순간 이전 결과나 에러는 타입 차원에서 아예 존재할 수 없게 되니, 손으로 일일이 비워줄 대상 자체가 없어진 거예요. 자연스럽게 `finally` 블록도 필요 없어졌어요.

화면을 그리는 렌더링 쪽 코드도 판별자를 활용해 타입을 좁혀서 읽어오면 돼요.

```tsx
<button disabled={generation.status === "loading"}>
  {generation.status === "loading" ? "생성 중..." : "단일 생성"}
</button>

{generation.status === "error" && <pre>{generation.message}</pre>}
```

이제 `generation.status === "error"` 조건문 안에서만 `generation.message`에 안전하게 접근할 수 있어요. 에러가 아닌 다른 상태일 때 에러 메시지를 읽으려고 하면 컴파일러가 알아서 막아줘요.

## 판별 유니온 도입으로 달라진 점

가장 먼저 표현 가능한 상태의 경우의 수가 여덟 가지에서 네 가지로 대폭 줄었어요. 기존의 `loading`, `localResult`, `error` 조합은 2×2×2로 총 여덟 가지였고 그중 절반인 네 가지는 현실에서 말이 안 되는 값들이었는데, 판별 유니온을 도입하면서 딱 유효한 네 가지만 만들 수 있게 되었어요. 없애버린 네 가지 조합이 바로 온갖 버그가 숨어들던 자리였던 셈이에요.

호출해야 하는 setter의 개수도 세 개에서 단 하나로 줄어들었어요. 코드의 정확성을 담보하는 방식이 "매번 개발자가 세 setter를 올바른 순서로 빠짐없이 부른다"는 피곤한 규칙에서, "새로운 상태 객체 하나로 갈아끼운다"는 단단한 타입 보장으로 전환되었어요.

재생성에 실패했을 때 이전 결과가 화면에 그대로 남아 있거나, 로딩 플래그가 꺼지지 않거나, 렌더링 분기 순서에 따라 엉뚱한 화면이 나오는 문제들을 겪곤 하잖아요. 앞에서 걱정하던 이 세 가지 위험 요소가 이제 코드 리뷰나 꼼꼼함에 기대는 게 아니라, 컴파일러가 알아서 원천 차단해 주는 안전한 구조가 되었어요.

## 안티패턴 재발을 방지하는 기준과 타입 테스트

이런 실수의 재발을 막으려면 결국 앞서 정리한 두 가지 질문을 팀 내부의 공용 기준으로 자리 잡게 만드는 것이 중요해요. 상호배타적인 상태를 새롭게 설계할 때, 각 상태가 자기만의 데이터를 품고 있고 한 번의 상태 전이가 여러 setter를 동시에 건드린다면 판별 유니온으로 단단하게 묶어줘요. 반대로 그런 경우가 아니라면 단순한 상태 문자열 하나만으로도 충분해요.

이 기준을 팀 학습 문서에 형태 A(상태를 단일 객체로 묶기)와 형태 B(판별자만 분리하고 나머지는 따로 두기)로 나누어 명확히 기록해 두었어요. 판별자 곁에 남겨둔 다른 상태가 특정 갈래에만 귀속되는 데이터인지, 아니면 모든 갈래와 무관하게 동작하는 보조 상태인지까지 명확히 감별할 수 있도록 가이드를 정리했어요.

여기에 더해 타입 차원에서 구조가 무너지는 걸 막아주는 회귀 방지 장치도 하나 추가할 수 있어요. 판별 유니온으로 짠 상태는 타입 수준의 테스트 코드로 검증해 둘 수 있거든요.

```ts
type Tagged =
  | { status: "loading" }
  | { status: "success"; result: Output }
  | { status: "error"; message: string };

// @ts-expect-error 로딩이면서 결과를 갖는 값은 만들 수 없어야 한다
const illegal: Tagged = { status: "loading", result };
```

`@ts-expect-error`는 바로 다음 줄에서 컴파일 에러가 터지기를 기대하는 특별한 지시자예요. 훗날 누군가 무심코 타입을 다시 flat한 boolean 형태로 되돌려서 위와 같은 말도 안 되는 조합이 문법적으로 합법이 되어버리면, `@ts-expect-error` 부분에 즉시 빨간 줄이 뜨면서 빌드가 멈추게 돼요.
