어노테이션 vs as const vs satisfies — 맵 상수에 뭘 붙여야 할까요

타입 어노테이션과 as const, satisfies의 차이를 짚어보고, 프로젝트 내 100여 개 Record 상수 중 satisfies가 실제로 득이 되는 기준을 정리했습니다.

기본기를 다시 다져보면서 satisfies 연산자를 다시 마주쳤어요. 평소 저희 팀 코드베이스에서는 자주 쓰지 않던 녀석이라, 그동안은 마주쳐도 가볍게 넘기곤 했는데요. 이번 글에서는 satisfies를 언제 써야 올바른지, 그리고 실제로 리팩토링했을 때 어떤 효과를 얻을 수 있는지 이야기해 보려고 해요.

satisfies의 동작 방식을 뒤늦게 제대로 이해하고 나니, 코드베이스 곳곳에 흩어져 있던 Record<...> 상수들이 전부 눈에 밟히기 시작했어요. 이걸 전부 satisfies로 교체하면 타입이 더 좁고 안전해지지 않을까 싶었죠. 무작정 바꾸기 전에 우선 개수부터 확인해 봤는데요. 타입 어노테이션이 붙은 객체나 배열 리터럴 상수가 프로젝트 전체에 100곳 남짓 있더라고요.

결국 satisfies를 도입할 때 가장 까다로운 부분은 "이 상수에서 교체하는 게 과연 이득인가, 아니면 손해인가"를 명확히 가려내는 작업이에요. 이번 글은 그 경계선을 어디에 그어야 할지 차근차근 짚어보는 여정입니다.

어노테이션, as 단언, satisfies를 나란히 비교해 보면#

객체 리터럴에 타입을 지정하는 방법은 크게 세 가지가 있어요. 동일한 객체에 세 가지 방식을 각각 나란히 적용해 보면 차이점이 명확하게 드러납니다.

type Keys = "a" | "b" | "c" | "d";

// 1) 어노테이션
const p1: Record<Keys, unknown> = { a: 0, b: "hello" };
//    p1.a 의 타입은 unknown. a 가 number 였다는 사실이 사라집니다.

// 2) as 단언
const p2 = { a: 0, b: "hello" } as Record<Keys, unknown>;
//    검사를 건너뜁니다. 틀린 타입을 우겨넣어도 통과합니다.

// 3) satisfies
const p3 = { a: 0, b: "hello", x: 8 } satisfies Record<Keys, unknown>;
//    x 는 Keys 에 없으므로 에러. 검사는 하되,
//    p3.a 는 number, p3.b 는 string 으로 좁게 유지됩니다.

타입 어노테이션은 객체가 대상 타입을 만족하는지 꼼꼼하게 검사해 줘요. 하지만 그 대가로 변수의 타입 자체를 명시된 어노테이션으로 굳혀 버립니다. 즉 p1의 타입은 Record<Keys, unknown>으로 고정되고, 원래 a가 number 타입이었다는 좁은 정보는 통째로 사라져요. 반대로 as 단언은 컴파일러의 타입 검사 자체를 아예 건너뜁니다. 컴파일러를 향해 "그냥 이 타입이라고 믿어 줘"라고 강제하는 셈이라, 엉뚱한 값을 집어넣어도 오류를 잡아내지 못하죠.

satisfies는 정확히 이 둘의 장점만 취한 형태예요. 타입 어노테이션처럼 객체가 특정 조건을 만족하는지 철저히 검사하면서도, 변수의 실제 타입은 리터럴에서 자연스럽게 추론된 좁은 형태 그대로 유지해 줍니다. 덕분에 p3.a의 타입은 unknown으로 흐려지지 않고 number로 남으며, 조건에 정의되지 않은 키 x가 들어오면 그 자리에서 컴파일 오류를 띄워 줘요. "이 객체가 타입 T의 규격을 제대로 갖췄는지 확인은 거치되, 변수 타입은 내가 작성한 값 그대로 좁게 유지해서 쓰고 싶다"는 요구가 있을 때 바로 이 satisfies를 쓰면 됩니다.

여기에 as const까지 함께 비교 선상에 올려두어야 뒤이어 나올 이야기들이 헷갈리지 않아요. 위의 예시에 나온 단순 as는 "이 타입이라고 치자"며 강제로 덮어씌우는 타입 단언이지만, as const는 리터럴 값 자체를 읽기 전용(readonly)이면서 가장 좁은 리터럴 타입으로 확정 짓는 도구예요. 뒤에서 살펴볼 최종 수정 코드나 DISH_TYPE_CODES에서도 이 as const가 계속 등장하니까요, 도구들의 특성을 표로 한 번 정리해 볼게요.

도구검사변수 타입
어노테이션 : TOT로 넓힘 (키 정보 손실)
as constX좁힘 + readonly
satisfies TO추론된 좁은 타입 유지

as const와 satisfies는 타입을 "좁게 유지한다"는 성격 때문에 하나로 묶여서 이해되곤 하지만, 결정적인 차이는 바로 검사 여부에 있어요. as const는 리터럴이 특정 규격을 만족하는지 검사하지 않고, satisfies는 명시된 대상 타입에 맞는지 철저히 검사하거든요. 이 검사 유무라는 한 칸의 차이가 실전에서 매우 큰 결과로 이어집니다.

타입 어노테이션이 검사를 해주는 대신 타입을 넓혀버리는 문제#

문제는 타입 어노테이션이 타입을 넓혀버리는 동작이 조용하게 잠재적 버그를 키운다는 점이에요. 실제 프로젝트 코드에는 이런 상수가 선언되어 있었어요.

// src/shared/config/constants/recipe.ts
export const INGREDIENT_CATEGORY_CODES: Record<string, string> = {
  전체: "",
  고기: "meat",
  채소: "vegetable",
  // ... 한글 카테고리 키 13개
};

여기서 Record<string, string>은 "키로는 어떤 문자열이든 다 받을 수 있고, 값은 string이다"라는 의미입니다. 그런데 이 어노테이션을 붙이는 순간, TypeScript는 객체 안에 실제로 선언된 13개의 구체적인 한글 키를 완전히 잊어버려요. 그래서 나중에 keyof typeof INGREDIENT_CATEGORY_CODES를 조회해 보면, 실제 정의된 13개의 키가 나오는 게 아니라 string | number가 튀어나오게 됩니다.

이 넓힘이 왜 위험한지는 이 상수를 가져다 쓰는 소비처 코드를 보면 곧바로 알 수 있어요.

// src/entities/ingredient/model/api.ts
category: category
  ? INGREDIENT_CATEGORY_CODES[
      category as keyof typeof INGREDIENT_CATEGORY_CODES
    ]
  : null,

이 코드에서 category 변수의 타입은 string | null이에요. 그런데 앞서 확인했듯 keyof typeof INGREDIENT_CATEGORY_CODES의 결과는 string | number이기 때문에, category as keyof typeof ...라는 타입 단언은 사실상 category as string과 다를 바가 없습니다.

겉으로 보기에는 유효한 카테고리 키로 안전하게 좁혀주는 타입 가드처럼 보이지만, 실제로는 타입 관점에서 아무런 필터링도 해주지 못하는 거예요. 여기에 실수로 "고기류" 같은 오타를 넣거나 심지어 "asdf" 같은 무의미한 문자열을 전달해도, 컴파일러는 아무런 의심 없이 통과시켜 버립니다.

타입이 넓어졌을 때 위험한 이유가 바로 여기에 있어요. 타입이 넓어지는 현상은 상수 정의 한 줄에서 일어나지만, 그 상수를 참조하는 수많은 소비처는 모조리 넓어진 타입을 그대로 물려받게 되거든요. 값이 실제로 소비되는 지점, 이를테면 네트워크 요청을 보내는 경계까지 거리가 멀어질수록 잘못된 값은 훨씬 늦게 발견될 수밖에 없어요. 정작 타입 시스템은 선언부 첫 줄에서 이미 손을 놓아버린 상태였던 셈이죠.

어노테이션을 걷어내고 satisfies로 바꿨을 때 드러난 효과#

그래서 문제의 상수에서 어노테이션을 걷어내고, 설정 객체를 유니온 타입의 단일 원천(Single Source of Truth)으로 재구성해 보았어요.

export const INGREDIENT_CATEGORIES = ["전체", ...INGREDIENT_CATEGORIES_BASE] as const;
export type IngredientCategoryName = (typeof INGREDIENT_CATEGORIES)[number];

export const INGREDIENT_CATEGORY_CODES = {
  전체: "",
  고기: "meat",
  // ...
} satisfies Record<IngredientCategoryName, string>;

이렇게 구조를 바꾸고 나면 keyof typeof INGREDIENT_CATEGORY_CODES는 비로소 실제 정의된 13개 키의 유니온("전체" | "고기" | ... | "기타")으로 정확하게 추론돼요. 소비처에 남아 있던 as keyof typeof 캐스트도 그제야 실질적인 타입 검사 역할을 수행하게 되고, 여기서 추출한 IngredientCategoryName 타입을 상태 관리, 이벤트 핸들러, API 통신 경계까지 두루 재사용할 수 있게 됩니다.

다만 여기서 각 도구가 해낸 역할을 명확하게 구분해 볼 필요가 있어요. 키 유니온을 온전하게 되살려낸 일등 공신은 엄밀히 말해 satisfies가 아니라 어노테이션을 제거한 행위 자체입니다. 기존의 : Record<string, string>이 keyof 결과를 string | number로 뭉개고 있었으니, 그 어노테이션을 지우는 즉시 객체 리터럴에서 추론된 13개의 구체적인 키 정보가 살아난 것이죠. satisfies가 담당한 일은 그렇게 비워진 자리에 객체의 형태를 검증하는 역할을 다시 채워 넣은 것뿐이에요. 어노테이션이 '타입 검증'과 '타입 넓힘'을 세트로 묶어서 강제하던 것을, 검증(satisfies)과 좁은 타입 추론(어노테이션 제거)이라는 두 개의 분리된 축으로 쪼개준 셈입니다. 그렇기 때문에 satisfies를 붙이지 않고 어노테이션만 지웠더라도 뒤에 나올 두 버그는 똑같이 컴파일 에러로 잡혔을 거예요. satisfies만이 해낼 수 있는 고유한 역할은 그 이후의 단계에 있습니다.

타입 체인을 처음부터 끝까지 촘촘하게 연결하자마자, 그동안 넓은 string 타입 뒤에 숨어 있던 진짜 버그 두 개가 컴파일 오류로 튀어나왔어요. 하나는 레시피 생성 화면에 있던 "나의 재료" 탭이었습니다. 이 값은 음식 카테고리가 아니라 사용자 본인의 냉장고 재료를 불러오는 필터였는데, 그동안 카테고리인 척 코드 매핑 로직을 타고 흐르다가 런타임에서 undefined를 반환하고 있었더라고요.

다른 하나는 그 "나의 재료" 탭을 판별하는 과정에서 다국어 지원용 사전 문자열("My Ingredients")과 직접 비교하고 있어서, 한국어가 아닌 다른 언어 환경에서는 "내 재료" 필터가 아예 활성화되지 않던 결함이었습니다. 둘 다 넓은 타입에 가려져 있던 런타임 버그였고, 타입을 실제 키 유니온으로 좁히자마자 즉시 수면 위로 드러났어요.

그리고 이 지점부터가 바로 satisfies만의 독보적인 가치예요. 어노테이션을 떼어낸 작업이 키 유니온을 되살려 주었다면, 뒤에 붙은 satisfies Record<IngredientCategoryName, string>는 이 코드맵 객체가 13개의 카테고리 키를 단 하나도 빠뜨리지 않고 구현했는지를 강제해 줍니다. 나중에 새로운 카테고리를 추가해 두고 코드 맵 매핑을 누락한다면, 빌드 시점에 그 자리에서 컴파일 오류를 뿜어내게 되죠.

이 빈틈없는 검증은 as const만으로는 해낼 수 없어요. "어노테이션 떼어내고 그냥 as const만 달아두면 충분하지 않나?"라는 의문이 생길 수 있지만, as const는 규격 검사를 전혀 하지 않기 때문에 키 13개 중 하나가 빠진 12개짜리 객체도 그저 12개짜리 좁은 타입으로 정상 통과시켜 버립니다. 목표로 하는 대상 타입(Record<IngredientCategoryName, string>)과 꼼꼼히 대조하면서 누락된 키를 컴파일 타임에 잡아주는 도구는 검사 기능을 갖춘 satisfies뿐이에요. 이건 런타임 타입 가드로도 사전에 예방하기 힘든 영역이기도 하고요.

satisfies가 오히려 타입 에러를 일으키는 상황과 판별 기준#

그렇다면 남아 있는 다른 상수들도 전부 satisfies로 바꾸면 될까요? 여기서 문제가 생깁니다. Record<string, V> 형태의 어노테이션을 무턱대고 satisfies로 교체하면 객체의 index signature가 사라져 버려요. 즉 [k: string]이라는 "임의의 문자열로 얼마든지 인덱싱해도 괜찮다"는 타입 시스템과의 사전 약속이 사라지고, 오직 코드에 적힌 구체적인 키들만 허용하는 닫힌 객체가 됩니다. 그 결과 임의의 동적 문자열 변수를 넘겨서 값을 조회하던 기존 코드들이 모조리 컴파일 에러를 뿜게 돼요.

// value 가 string 이라, index signature 가 없으면 인덱싱 불가
DISH_TYPE_ICONS[value];
DAY_UNIT[locale];
COOKING_METHOD_ICON[trimmed];
REFERRAL_ERROR_MESSAGES[code];

이런 상수 맵들은 태생 자체가 외부에서 들어오는 임의의 문자열 입력을 받아 유연하게 룩업하기 위한 용도예요. 따라서 [k: string]이라는 index signature 약속이 유지되어야만 정상적으로 동작합니다. 이런 자리의 타입을 굳이 좁혀버리는 건 개선이 아니라 오히려 기존 동작을 깨뜨리는 회귀에 불과해요.

처음부터 넓은 타입으로 두는 것이 설계 의도에 완벽히 부합하는 사례도 있습니다. NOTIFICATION_STATUSES나 PLATFORMS 같은 상수는 readonly string[] 타입으로 선언되어 있고, 실제 코드에서는 .includes(p.status)처럼 외부에서 들어온 임의의 문자열 인자를 넘겨 유효성을 검사하는 용도로 쓰여요. 여기에 무턱대고 as const를 붙여 좁은 튜플 타입으로 만들어 버리면, .includes 메서드가 해당 튜플에 속하지 않는 임의의 문자열 인자를 거부하기 때문에 멀쩡하던 컴파일이 깨지게 됩니다. 이때 컴파일을 깨뜨리는 원인은 타입을 좁혀버린 as const이지 satisfies 자체가 아니에요. 실제로 satisfies readonly string[]는 타입을 좁히지 않고 형태만 검사하므로 문법적으로는 아무런 문제가 없죠. 다만 애초에 넓은 타입으로 두는 것이 정답인 자리인 만큼, 굳이 추가 선언을 덧붙일 실익도 없습니다.

결국 판별 기준은 아주 명확하게 정리할 수 있어요. 구체적으로 좁혀진 키 집합을 소비하는 코드가 존재한다면 satisfies를 쓰는 것이 이득이고, 임의의 문자열 변수로 조회해야 해서 index signature가 필요한 자리라면 satisfies는 오히려 방해가 됩니다. 이를 상황별로 정리하면 다음과 같아요.

그 상수를 이렇게 쓰고 있다면satisfies
keyof typeof로 키 union을 뽑아 쓴다이득
리터럴 키로 접근하되 값 타입은 안 쓴다 (X.고기)이득 없음
값을 리터럴 타입 그대로 소비한다이득 (as const satisfies)
임의의 string 변수로 인덱싱한다 (X[key])깨짐 — index signature 필요
배열을 map / iterate만 한다이득 없음

기존 코드에 숨어 있던 올바른 패턴과 팀 차원의 작성 규칙#

흥미롭게도 올바른 작성 패턴은 문제가 되었던 상수 바로 곁에 이미 자리 잡고 있었어요. 같은 recipe.ts 파일 내부를 들여다보니 이렇게 구현되어 있더라고요.

// 정답: 어노테이션 없이 as const
export const DISH_TYPE_CODES = {
  전체: null,
  볶음: "FRYING",
  // ...
} as const;

export type DishType = keyof typeof DISH_TYPE_CODES; // 실제 키 union

// 바로 아래: 어노테이션이 as const 를 죽인 코드
export const DISH_TYPE_ICONS: Record<string, string> = {
  전체: "all.webp",
  // ...
} as const;

먼저 선언된 DISH_TYPE_CODES는 불필요한 어노테이션을 달지 않았기 때문에, keyof typeof를 통해 실제 정의된 키 유니온을 그대로 추출할 수 있고 DishType 또한 의도대로 좁은 타입으로 정확히 도출돼요. 반면에 바로 아래 줄의 DISH_TYPE_ICONS를 보면, 뒤쪽에 as const를 분명히 달아두었음에도 불구하고 앞부분에 : Record<string, string>이라는 어노테이션이 붙어 있어서 as const가 아무런 효력을 발휘하지 못하고 있습니다. 조금 더 구체적으로 짚어보자면, as const가 리터럴을 좁은 타입으로 추론해 놓아도 앞의 어노테이션이 변수 타입을 다시 Record<string, string>으로 강제로 넓혀버려요. 결국 타입을 좁히려고 애써 붙여둔 as const의 연산 결과가 그 자리에서 폐기되어 죽은 코드로 남아버린 셈이죠.

여기서 팀원들과 함께 공유할 만한 실질적인 규칙을 도출할 수 있어요. 새로운 맵 상수를 정의할 때는 습관적으로 : Record<...> 어노테이션을 달지 말고 as const나 satisfies를 활용해 선언하고, 키 타입이 필요할 때는 keyof typeof를 통해 유연하게 파생해서 씁니다. 타입 어노테이션은 타입을 명시적으로 적어주니 왠지 코드가 더 안전해졌다는 안도감을 주지만, 실제로는 우리가 필요로 하는 핵심적인 키 정보를 지워버리는 원인이 되기 때문이에요.

앞으로 코드 리뷰에서 눈여겨봐야 할 체크포인트 역시 아주 직관적입니다. 만약 : Record<string, ...> = { 형태로 선언된 리터럴 상수가 보인다면, 해당 상수의 키를 keyof typeof로 참조해서 사용하는 곳이 있는지부터 확인해 보세요. 그런 사용처가 존재한다면 그 keyof는 지금 string으로 느슨하게 새어나가고 있는 상태이니 satisfies로 개선할 훌륭한 후보가 됩니다. 반대로 그런 추출 없이 외부의 임의 문자열 변수로 조회만 하는 룩업 테이블이라면, 기존처럼 index signature를 유지해 주는 어노테이션 형태가 올바른 선택이에요.

마치며#

이번 글에서는 TypeScript의 satisfies 연산자를 깊이 있게 살펴보면서, 좁은 타입의 안전성을 실제로 어떻게 살릴 수 있는지 정리해 보았어요. 더불어 타입 어노테이션과 as const를 한곳에 동시에 선언했을 때 어노테이션의 넓힘 동작 때문에 as const가 무력화되어 죽은 코드가 된다는 사실도 명확히 배울 수 있었습니다.
