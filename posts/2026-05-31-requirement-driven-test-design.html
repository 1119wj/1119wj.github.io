AI 에이전트에게 테스트 작성을 맡겼다가 개발 병목을 겪은 이야기

TDD에 AI 에이전트를 도입하고 두 달 뒤 테스트가 오히려 병목이 되었던 원인과, 중복 검증 및 레이어 분해의 함정을 거쳐 행동 슬라이스로 개선한 과정을 공유합니다.

두 달 전쯤 제 작업 흐름에 TDD 방식을 하나 붙여보았어요. 새 기능을 구현하기 전에 먼저 테스트부터 설계하고, Claude Code 같은 AI 에이전트가 그 테스트를 따르면서 코드를 작성하게 만드는 흐름이었죠. 처음에는 좋았어요. 그런데 두 달쯤 지나고 나니, 역설적으로 테스트 코드가 전체 기능 개발 속도를 가로막는 가장 큰 병목이 되어 있더라고요.

테스트 실행 속도(런타임) 자체가 느려져서 생긴 문제는 아니었어요. 테스트 파일이 걷잡을 수 없이 쌓이면서, 에이전트가 매 작업마다 읽고 유지보수해야 할 맥락이 너무 커졌거든요. 컨텍스트 윈도우와 토큰 소모량이 심각한 병목을 일으키고 있었던 거예요.

문제를 깨닫고 한 슬라이스를 날 잡아서 정리해 보니 테스트 수가 90개에서 78개로 줄었어요. 사실 단순히 숫자를 쳐내는 일 자체는 어렵지 않았어요. 진짜 어려웠던 건 '남겨야 할 78개를 어떤 기준으로 골라낼 것인가'였고, 원인을 더 파고들어 보니 '테스트 개수를 줄인다'는 행위 자체가 근본적인 해결책도 아니었어요. 문제의 뿌리는 테스트 코드보다 훨씬 윗단에 자리 잡고 있었거든요.

어쩌다 테스트가 이렇게 쌓이게 되었는지, 부끄러운 코드부터 차근차근 짚어볼게요.

에이전트가 만든 테스트 파일을 열어보고 놀랐던 이유#

보통 에이전트에게 "이 기능 테스트 코드 좀 짜줘"라고 가볍게 프롬프트를 던지면, 30초도 안 되어서 테스트 스위트가 한 무더기 쏟아져 나와요. 터미널을 돌려보면 전부 깔끔하게 초록불이 뜨고 커버리지 그래프도 빈틈없이 예쁘게 채워지죠. 그런데 하루는 그 안을 자세히 뜯어보았어요.

컴포넌트 하나를 테스트하는 파일인데 상단에 jest.mock이 열다섯 개나 붙어 있더라고요. 라우터도 가짜, 전역 스토어도 가짜, API 호출부도 모조리 가짜로 둘러쳐져 있었어요. 다른 테스트 파일을 열어봤더니 더 가관이었어요. LLM 프롬프트 템플릿 문자열 안에 "정확히 5"라는 글자가 그대로 들어 있는지 정규식으로 검사하고 있더라고요.

expect(sys).toMatch(/h1.*dek.*숫자.*정확히.*5/);

또 다른 파일에서는 crypto.randomUUID가 표준 UUID 규격에 맞는 값을 뱉는지 확인하겠다고 반복문을 돌려 백 번씩 확인하고 있었고요.

누굴 탓할 수도 없는 게, 다 제가 시키고 제가 프롬프트를 준 에이전트가 작성한 코드였어요. 너무 부끄럽지만 솔직한 반성을 위해 박제해 두고 넘어가려고 해요. 그런데 이런 엉터리 모킹이나 불필요한 단언을 걷어내는 건 사실 아주 기본적인 테크닉에 불과해요. 저를 훨씬 더 오래 괴롭혔던 문제는 따로 있었거든요. 그걸 제대로 짚으려면 먼저 '좋은 테스트란 무엇인가'에 대한 기준부터 명확하게 세워야 해요.

좋은 테스트는 오직 행동이 깨질 때만 실패해야 해요#

제가 생각하는 좋은 테스트는 딱 한 문장으로 정리할 수 있어요. '사용자 관점의 행동이 깨질 때 실패하고, 오직 그때만 실패하는 테스트'예요. 이 짧은 문장 뒤집어보면 우리가 피해야 할 치명적인 실패 유형 두 가지가 그대로 드러나요.

첫 번째는 코드가 실제로 깨졌는데도 테스트는 그냥 통과해 버리는 경우예요. 버그가 버젓이 프로덕션으로 새어나가게 되죠. 두 번째는 비즈니스 로직이나 동작은 전혀 깨지지 않았는데 내부 구현이 조금 바뀌었다고 빨간 불이 켜지는 경우예요. 안전하고 정당한 리팩터링인데도 매번 테스트가 깨지다 보니, 결국 리팩터링을 주저하게 만드는 거대한 세금이 되어버려요.

저는 앞의 경우를 '거짓 통과', 뒤의 경우를 '헛경보'라고 불러요. 정식 소프트웨어 공학 용어로는 각각 false negative와 false positive에 해당해요. 화재경보기에 빗대어 보면 이해하기 쉬워요. 집에 불이 활활 났는데 경보기가 울리지 않는 게 '거짓 통과'이고, 불은커녕 연기도 안 났는데 시끄럽게 울려대는 게 '헛경보'인 셈이죠.

앞서 보여드린 부끄러운 테스트 갤러리도 대부분 이 두 범주 안에 쏙 들어가요. 가짜 객체 열다섯 개로 둘러싸인 테스트는 실제 프로덕션 코드가 아니라 제가 손수 적어둔 목(mock)의 동작을 검증하고 있으니 버그를 못 잡는 거짓 통과가 되기 쉽고요. 프롬프트 문구 안의 글자 하나하나를 정규식으로 검증하는 테스트는 프롬프트 문장만 조금 다듬어도 우수수 깨져버리니 전형적인 헛경보를 만들어내죠.

이런 문제를 막기 위한 기본 원칙 자체는 명확해요. 내부 구현 방식(어떻게)을 시시콜콜 베끼지 말고 최종적인 행동(무엇)을 검증할 것, 네트워크나 시간, 외부 라이브러리처럼 내가 소유하지 않은 경계 지점만 모킹할 것, 하이퍼파라미터나 튜닝 수치는 값을 그대로 박아 넣지 말고 단조성이나 유효 범위 같은 성질을 중심으로 검증할 것. 개발자라면 누구나 고개를 끄덕일 만한 원칙이고, 프롬프트 규칙 몇 줄로도 어느 정도 정리할 수 있는 내용이에요. 하지만 진짜 문제는 이 기본기를 꼼꼼히 지켜도 여전히 풀리지 않는 지점이 있었다는 사실이에요.

레이어마다 같은 동작을 세 번씩 중복 검증하고 있었어요#

저희 프로젝트는 FSD(Feature-Sliced Design) 아키텍처를 꽤 엄격하게 적용하고 있어요. 레이어 간의 의존성 방향을 규칙으로 강제하죠. 예를 들어 shared 레이어는 상위 레이어를 전혀 알지 못하고, feature 레이어는 하위 entity 레이어를 가져와서 조립하는 식이에요. 그런데 코드베이스에는 이렇게 엄격한 규율을 두었으면서, 정작 테스트 코드에는 그런 레이어별 책임과 위계가 전혀 없었어요.

유튜브 링크를 가져와 처리하는 import 슬라이스를 분석하다가 놀라운 장면을 목격했어요. 백엔드 에러 코드를 사용자 안내 메시지로 변환해 주는 로직 하나가 무려 세 군데 파일에서 똑같이 검증되고 있더라고요.

// lib/errors.test.ts — 순수 함수가 변환을 소유
it("907 → 유튜브 링크만 가능해요", ...)

// model/useJobPolling.test.tsx — 훅 테스트에서 또
expect(job.message).toBe("유튜브 링크만 가능해요")

// ui/...test.tsx — 컴포넌트 테스트에서 또

커스텀 훅도, UI 컴포넌트도 그 에러 메시지 변환 로직에 어떤 추가적인 가치도 더하지 않아요. 그저 하위에 정의된 순수 유틸 함수를 호출할 뿐인데, 똑같은 동작 보장을 세 군데 레이어에서 각자 비용을 치르며 사고 있었던 셈이에요. 테스트 작성과 유지보수 비용은 세 배로 드는데 버그를 잡아내는 효율은 그대로이고, 심지어 에러 문구를 하나 바꾸면 세 개 파일이 한꺼번에 빨갛게 물들게 돼요.

그래서 코드 작성에 쓰던 FSD의 책임 분격 개념을 테스트에도 그대로 적용해 보기로 했어요. '어떤 행동은 그 행동이 정의되는 가장 낮은 레이어가 온전히 소유한다'는 원칙을 세운 거죠. 에러 코드 변환은 순수 함수가 담당하고 있으니 순수 함수 테스트에서만 딱 한 번 검증해요. 그 상위 레이어는 오직 자기 자신만이 검증할 수 있는 고유한 책임만 맡도록 했어요. 예컨대 폴링 훅이라면, 순수 함수 레벨에서는 결코 다룰 수 없는 '동일한 작업이 폴링 도중 중복 처리되지 않는다'는 식의 멱등성 보장만 집중해서 테스트하는 식이에요. (물론 FSD는 원래 코드 구조를 잡는 아키텍처이지 테스트 방법론은 아니기 때문에, '테스트에도 FSD를 적용한다'는 건 제가 상황을 설명하기 위해 빗댄 표현이에요.)

이 단순한 원칙 하나를 적용해서 해당 슬라이스를 정리했더니, 테스트 개수가 90개에서 78개로 깔끔하게 줄어들었어요. 덜어낸 12개는 모조리 중복 검증이거나 헛경보를 유발하던 군더더기였고, 사용자가 체감하는 실질적인 기능 커버리지는 단 하나도 줄어들지 않았어요.

그런데 완전히 똑같은 원칙을 들고 바로 옆 슬라이스에 적용해 보았을 때는 정반대의 결과가 나타났어요. 유튜브 import 기능 옆에는 AI가 레시피를 자동으로 생성해 주는 슬라이스가 쌍둥이처럼 붙어 있었거든요. 작업 상태를 주기적으로 확인하는 폴링 구조도 거의 판박이였고요. 코드를 열어보니 유튜브 슬라이스와 똑같은 중복 검증 문제가 있었는데, 여기는 한술 더 뜬 상태였어요. 상태를 관리하는 스토어 자체를 독립적으로 검증하는 테스트 파일이 아예 존재하지 않았던 거예요.

그러다 보니 중복 작업을 방지하거나 진행 중인 작업을 걸러내는 스토어 본연의 행동을 테스트하기 위해, 목(mock) 일곱 개를 덕지덕지 바른 무거운 폴링 훅 테스트를 거쳐서 간접적으로 확인하고 있었어요. 절반은 그렇게 비싼 비용을 치르는 훅 테스트에서 어색하게 검증되고 있었고, 나머지 절반은 어디서도 검증되지 못한 채 방치되어 있었죠.

그래서 이 슬라이스도 책임을 제자리로 돌려주었어요. 스토어가 맡아야 할 행동은 목이 0개 들어간 가벼운 스토어 단위 테스트로 내리고, 상태 값을 가공하는 로직은 순수 함수로 똑 떼어내서 역시 목이 0개인 매핑 테스트로 분리했어요. 결과가 무척 흥미로웠어요. 전체 테스트 개수는 기존 23개에서 35개로 오히려 늘어났거든요. 하지만 가짜 객체로 칭칭 감겨 있던 무거운 테스트는 12개에서 4개로 대폭 줄었고, 새로 늘어난 테스트는 전부 목이 하나도 없는 가볍고 순수한 테스트들이었어요.

유튜브 슬라이스에서는 테스트 수가 줄었고, AI 슬라이스에서는 오히려 늘어났지만 두 사례가 말해주는 본질은 완전히 같아요. 레이어별로 책임을 명확히 나눈다는 건 '단순히 테스트 숫자를 줄이는 작업'이 아니에요. 각 행동을 검증 비용이 가장 저렴한 한 곳을 찾아 딱 한 번만 제대로 검증하자는 뜻이죠. 중복이 많았던 곳은 숫자가 줄어들고, 마땅히 있어야 할 자리가 비어 있던 곳은 채워지면서 숫자가 늘어나게 돼요. 테스트 개수의 증감은 올바른 책임을 찾아간 결과일 뿐, 그 자체가 목적이 되어서는 안 돼요.

여기까지 정리하고 나니 나름의 해결책을 찾았다고 생각했어요. 하지만 머릿속에 질문 하나가 계속 맴돌더라고요. '도대체 왜 유튜브 쪽에는 중복이 잔뜩 쌓였고, AI 쪽에는 빈자리가 숭숭 뚫려 있었을까?'

테스트 코드의 진짜 문제는 작업 분해 방식에 있었어요#

원인을 파고내려가다 보니, 답은 테스트 코드 자체가 아니라 그보다 한 단계 더 높은 작업 계획 단계에 있었어요. 두 슬라이스 모두 애초에 기능을 개발할 때 작업을 '기술 레이어' 기준으로 잘라두었기 때문이었어요.

새로운 기능을 구현할 때 보통 어떤 순서로 작업을 쪼개시나요? 대개 타입 정의하기, API 통신 함수 작성하기, 전역 스토어 만들기, 폴링 훅 구현하기, 마지막으로 UI 컴포넌트 붙이기 순서로 계획을 세우곤 하죠. 언뜻 보면 무척 체계적이고 깔끔해 보여요. 하지만 작업을 이렇게 레이어별로 가로로 자르면, 각 작업 티켓의 성격이 '어떤 사용자 가치를 만든다'가 아니라 '이 특정 구현 단위를 완성해라'로 굳어지게 돼요.

그리고 어떤 구현 단위를 독립된 작업으로 던져주면, 자연스럽게 그 단위만을 격리해서 확인하려는 무지성 유닛 테스트가 튀어나오게 돼요. 스토어 만드는 작업이 덩그러니 분리되어 있으니 스토어 내부 setter를 일일이 검증하는 유닛 테스트가 생겨나고, 폴링 훅 작업은 앞선 맥락과 뚝 떨어진 채 완성되어야 하니 가짜 객체 일곱 개를 억지로 끌어와서 훅을 감싸게 되는 거죠. 기술 레이어 중심의 작업 분해가 불필요하고 취약한 유닛 테스트들을 필연적으로 양산하고 있었던 거예요.

이 가설을 검증해보고 싶어서 작은 실험을 하나 해보았어요. 에이전트에게 새로운 기능 요구사항 하나를 주고, 아무런 가이드라인 없이 "구현 계획용 작업 목록으로 쪼개봐"라고만 시켜보았어요.

결과는 예상대로였어요. 두 에이전트 모두 데이터 모델 타입 정의부터 작업 목록 맨 위에 깔기 시작하더라고요. 심지어 한 번은 작업 목록 헤더를 아예 "데이터 레이어 / 상태 / 공유 / 횡단 관심사"로 나누더니, 첫 세 작업을 타입 정의, API 함수 작성, 쿼리 키 설정으로 채워 넣었어요. 정말 흥미로웠던 건, 그 에이전트가 저희 프로젝트의 테스트 설계 지침을 이미 알고 있는 상태였다는 점이에요. 답변 맨 마지막에 "실제 계획에선 테스트 설계 매트릭스를 먼저 돌려야 한다"라고 스스로 인용까지 해두었더라고요. 그렇게 좋은 테스트 설계 원칙을 머리로는 다 알면서도, 정작 작업을 쪼갤 때는 기계적으로 레이어를 분해해 버린 거예요.

여기서 아주 중요한 깨달음을 얻었어요. 아무리 좋은 테스트 작성 스킬과 매트릭스를 쥐어주어도, 작업을 분해하는 방식 자체가 잘못되어 있으면 좋은 테스트를 만들어낼 수 없어요. 기술 레이어로 잘라놓은 작업 위에 테스트 매트릭스를 얹어봐야, 매트릭스는 그저 각각의 레이어를 레이어 테스트로 기계적으로 1:1 매핑해 줄 뿐이거든요. 테스트는 결국 요구사항의 형태를 따라가는데, 그 요구사항을 개발자가 어떤 단위로 썰어두었느냐가 테스트의 전체적인 구조와 모양을 사전에 결정지어 버려요. 즉, 작업 분해 전략이 테스트 전략보다 훨씬 더 상위에 있는 문제였던 거죠.

그렇다면 작업을 어떻게 쪼개야 할까요?

기술 레이어가 아니라 사용자 행동 단위로 작업을 쪼개기#

해결책은 레이어가 아니라 '사용자의 행동'을 기준으로 작업을 수직으로 자르는 것이었어요. 사용자가 화면을 통해 직접 수행할 수 있고, 그 결과를 눈으로 명확히 확인할 수 있는 하나의 완결된 동작을 처음부터 끝까지 얇게 관통해서 잘라내는 거죠. 이렇게 하면 하나의 작업 슬라이스가 타입 정의, API 통신, 상태 스토어, UI 컴포넌트를 모두 관통하게 돼요. 딱 그 한 가지 행동을 완성하는 데 필요한 만큼만요.

예를 들어 "유튜브 링크를 입력받아 레시피로 변환해 가져오기"라는 기능이 있다면, 모델 타입 한 묶음 만들고 API 함수들 한 묶음 만드는 식이 아니라 이렇게 쪼개는 거예요. 첫 번째 슬라이스는 '사용자가 링크를 붙여넣으면 백그라운드 작업이 등록되고 진행률 바가 보인다', 두 번째는 '작업 처리가 완료되면 완성된 레시피 상세 화면으로 이동한다', 세 번째는 '처리에 실패하거나 지원하지 않는 링크라면 적절한 에러 화면을 보여준다'처럼 나누는 거죠.

이렇게 자르면 각각의 조각이 그 자체로 독립적인 데모가 가능해져요. 특히 가장 첫 번째 슬라이스는 전체 파이프라인을 가장 얇게 한 줄로 관통하는 작업이기 때문에, 내부 코드가 조금 투박하거나 못생겨도 괜찮아요. 소프트웨어 개발에서는 이런 방식을 '워킹 스켈레톤(walking skeleton)'이라고 불러요. 애자일 방법론의 대가인 앨리스터 코번(Alistair Cockburn)이 널리 알린 개념이죠. "일단 바닥 기반 작업부터 완벽하게 깔아두자"는 막연한 접근을, 얇게 동작하는 이 한 줄의 뼈대가 대신해 주는 거예요.

그리고 이렇게 나눈 슬라이스마다 반드시 세 가지 항목을 세트로 묶어서 작성하도록 했어요. 첫째, 이 작업이 끝났음을 정의하는 인수 기준(Acceptance Criteria), 둘째, 이번 작업에서는 의도적으로 구현하지 않는 비목표(Non-goals), 셋째, 하나의 도메인 개념을 프로젝트 전체에서 단 하나의 단어로 통일하기 위한 용어집이에요.

앞서 아무 규칙 없이 레이어로 쪼갰던 바로 그 기능 요구사항을 들고, 이번에는 이 행동 기반 슬라이싱 방식을 주면서 에이전트에게 다시 계획을 세우게 해보았어요. 그러자 작업 목록이 레이어가 아니라 사용자 행동 단위로 깔끔하게 나뉘었고, 각 슬라이스마다 명확한 인수 기준이 붙었으며, 무엇보다 이전 시도에서는 에이전트가 무심코 흘려보냈던 핵심 요구사항 하나—"초대받은 친구는 별도의 로그인이나 앱 설치 없이도 레시피를 열람할 수 있어야 한다"—를 누락하지 않고 온전한 인수 기준으로 끄집어내더라고요.

하지만 슬라이스를 아무리 예쁘게 썰어도 마음 한구석에 여전히 불안이 남았어요. 혹시라도 중요한 요구사항이 에이전트 모르게 조용히 빠져나가 버리면 어쩌지? 그리고 방금 언급한 '용어를 한 단어로 고정하는 일'은 대체 왜 필요한 걸까요?

누락을 막으려면 어디까지 안 만들지 먼저 합의해야 해요#

실제로 개발을 진행하다 보면 요구사항이 소리 소문 없이 증발하는 일이 심심찮게 일어나요. 예전에 에이전트에게 "친구가 로그인이나 앱 설치 없이 레시피를 본다"는 문장을 대충 던져주었더니, 에이전트가 "설치 없이"라는 조건을 통째로 누락한 채 코드를 짜놓고도 테스트는 전부 초록불을 띄운 적이 있었어요. 겉보기엔 테스트가 통과하니 사람이 꼼꼼히 리뷰하지 않으면 누락된 사실조차 눈치채지 못하죠.

처음에는 이 문제를 풀겠다고 꽤 거창한 시스템을 고민했어요. 모든 테스트 코드마다 고유한 요구사항 ID를 태그 형태로 박아 넣고, 요구사항 문서와 테스트 코드를 코드 레벨에서 1:1로 추적해서 만약 누락된 요구사항이 있으면 CI 단계에서 빌드를 깨뜨리도록 인프라를 만들어볼까 했죠. 하지만 설계를 진행하다가 이내 멈춰 섰어요. 이런 방식은 의료기기나 항공기 제어 소프트웨어처럼, 요구사항 하나가 빠지는 순간 곧장 인명 사고나 대규모 리콜로 이어지는 환경에서 쓰는 '요구사항 추적 매트릭스(RTM)' 기법이거든요. 거긴 그만한 무게와 비용을 치를 정당한 이유가 있지만, 고작 3명이서 만드는 레시피 웹 앱에서 태그 동기화 스크립트와 검증 도구를 유지보수하는 건 빈대를 잡으려다 초가삼간을 다 태우는 꼴이었어요.

그래서 복잡한 메타데이터 태그 대신, 지극히 자연스러운 '단어의 일치'를 통해 요구사항을 이어보기로 했어요. 기획 단계의 인수 기준에 "완료되면"이라는 표현이 쓰였다면, 코드 내부의 상태 값도 completed로 정의하고, 테스트 코드 역시 "completed 상태를 반환한다"라고 서술하는 식이에요. 기획, 코드, 테스트가 완전히 동일한 도메인 어휘를 공유하고 있다면 요구사항과 테스트를 잇는 추적선은 단어 그 자체로 이미 튼튼하게 연결돼요. 굳이 번거로운 ID 태그를 붙이지 않아도 되는 거죠. 도메인 용어를 기획부터 코드 베이스 끝까지 하나의 단어로 일관되게 끌고 올라가는 이 원칙을 도메인 주도 설계(DDD)에서는 '유비쿼터스 언어(Ubiquitous Language)'라고 불러요. 슬라이스 계획마다 용어집을 두고 단어를 고정했던 이유가 바로 여기에 있었던 거예요.

돌아보면 예전에 에이전트가 "주간 식단"이라는 기획 단어를 코드에서 슬그머니 "meal plan"으로 바꿔치기하거나, API 명세의 shareToken을 다른 컴포넌트에서는 slug라는 이름으로 제멋대로 부르던 현상이 있었는데, 그게 바로 요구사항의 추적선이 코드에 닿기도 전에 끊겨버리던 전형적인 신호였던 셈이에요.

그렇다면 애초에 요구사항이 통째로 빠지는 문제는 어떻게 막았을까요? 바로 '비목표(Non-goals)' 목록을 작성하면서 자연스럽게 해결되었어요. 만들지 않을 것들을 명시적으로 호명해 주면, 반대로 이번에 반드시 만들어야 할 범위가 닫힌 집합처럼 명확해지거든요. "앱 설치 없이 열람 가능"이라는 조건이 이번 작업의 인 스코프(in-scope)인지 아웃 스코프(out-of-scope)인지를 설계 단계에서 한 번만 딱 집어서 명시해 주면, 그 조건이 어느 쪽에도 속하지 못한 채 중간에서 흔적도 없이 증발하는 사고를 원천 차단할 수 있어요.

결국 테스트 전략에서 가장 고도화된 판단은 "어떻게 모든 것을 완벽하게 추적할까"가 아니라 "이번엔 어디까지 안 만들 것인가"를 합의하는 데 있더라고요. 요구사항과 테스트 코드는 평소에 느슨하게 분리된 상태로 두되, 슬라이스를 설계하는 바로 그 순간에만 서로의 싱크를 딱 한 번 정밀하게 맞춰보는 것. 3인 팀 규모에서는 이 정도의 느슨한 규율이 가장 건강하고 실용적인 적정선이었어요.

하지만 이런 훌륭한 원칙들도 사람이 일일이 감시하지 않으면 흐지부지되기 십상이죠. 에이전트가 매번 이 과정을 건너뛰지 않고 지키게 만들려면 어떻게 해야 할까요?

에이전트가 우회하지 못하도록 파이프라인에 가드레일 심기#

좋은 원칙을 세우는 것과, AI 에이전트가 그 원칙을 매 작업마다 실제로 준수하게 강제하는 것은 완전히 다른 차원의 문제예요. 프롬프트 시스템 지침에 "반드시 이 원칙을 지켜서 작업해"라고 아무리 근엄하게 적어두어도, 토큰이 길어지거나 서두르기 시작하면 그냥 쓱 무시하고 지나치기 일쑤거든요.

처음에는 전역 규칙에 "모든 구현에 앞서 무조건 이 단계를 거쳐야 한다"며 강력한 제약을 걸어보았어요. 그런데 마치 CSS에서 !important를 남발했을 때처럼 꼬이더라고요. 작업 단위의 세부 프롬프트에서는 "일단 빠르게 코드부터 확인해 봐"라고 지시하는데 상위 전역 규칙이 그걸 무조건 찍어누르려 하니 에이전트가 프롬프트 충돌을 일으키며 멍해지곤 했어요.

그래서 강제로 억누르는 대신, 에이전트가 지나갈 수 있는 길 자체를 외길로 좁히는 방식을 택했어요. 설계를 마치고 나면 곧바로 구현 코드로 넘어가지 못하고 반드시 행동 슬라이싱 단계를 거치도록 파이프라인을 짰어요. 슬라이스 정의와 각 슬라이스별 인수 기준 매트릭스가 산출물로 나오지 않으면, 구현 계획 단계 자체가 아예 실행을 거부하도록 아키텍처 레벨에서 막아버린 거죠. 우회로 자체를 치워버리니 구구절절 지시할 필요가 없어졌어요.

더 나아가 이 슬라이싱 파이프라인을 다듬는 과정 자체도 TDD 방식으로 접근했어요. 지침을 수정하기 전에 에이전트가 어떻게 실패하는지 그 취약점을 먼저 눈으로 확인한 거예요(Red). 앞서 말씀드렸듯 규칙을 주지 않았을 때 에이전트가 기계적으로 레이어 분해를 해버리던 모습이 바로 이 파이프라인의 실패 테스트였던 셈이에요. 규칙을 주입하자 비로소 행동 중심의 수직 슬라이스로 쪼개기 시작했죠(Green).

여기서 멈추지 않고 스트레스 테스트를 한 번 더 던져보았어요. 제가 성격 급한 테크 리드 역할을 맡아서 "데모 30분 남았으니 격식 차리지 말고 작업 목록만 빨리"라고 강하게 몰아붙여 본 거예요. 그랬더니 에이전트가 슬라이스 분할 자체는 용케 유지하면서도, 인수 기준 작성을 "생략 가능한 격식"으로 치부하고 쏙 빼먹더라고요.

그래서 그 구멍도 지침으로 틀어막았어요. 인수 기준은 슬라이스당 딱 한 문장으로 끝나는 가장 작성 비용이 저렴한 안전장치이며, 마감이 급박할수록 절대로 타협해서는 안 되는 핵심 요소라고 못을 박았죠. 그러고 나서 똑같은 압박 프롬프트를 다시 주었더니, 이번에는 촉박한 상황에서도 인수 기준 한 문장을 악착같이 챙겨서 계획을 내놓더라고요.

실제 실패 양상을 눈으로 확인하지 않고 머릿속으로만 작성한 프롬프트 지침은, 겉보기엔 그럴싸해 보여도 실전에서는 거의 작동하지 않는 공문서가 되기 쉬워요. 프로덕션 코드가 그렇듯 프롬프트 지침 역시, 의도적으로 빨간 불을 켜보고 실패하는 모습을 확인하기 전까지는 그것이 현실에서 무엇을 막아주고 있는지 결코 확신할 수 없거든요.

도구와 상관없이 사람이 리뷰할 때 던져야 할 질문들#

지금까지 Claude Code라는 에이전트를 중심으로 이야기를 풀었지만, 사실 마지막에 남은 본질적인 교훈들은 특정 AI 도구와는 아무런 상관이 없어요. 작업을 구현 기술 단위가 아니라 사용자 행동 단위로 쪼개는 것, 똑같은 비즈니스 로직을 불필요하게 여러 레이어에서 중복 검증하지 않는 것, 요구사항을 구현 전에 한 번 훑어보며 누락된 조건이 없는지 확인하는 것, 그리고 무엇보다 이번에 만들지 않을 것을 명확히 선 긋는 것.

이건 에이전트가 없더라도, 우리 개발자들이 동료의 풀 리퀘스트(PR)를 리뷰할 때 항상 머릿속으로 던져야 하는 가장 본질적인 질문들이에요. 저는 단지 에이전트가 그 중요한 질문들을 개발 과정에서 스스로 던질 수 있도록 환경과 가드레일을 마련해 준 것뿐이고요.

물론 아직 말끔히 닫지 못한 아쉬운 구멍도 하나 남아 있어요. 앞서 예시로 들었던 907 같은 에러 코드는 사실 백엔드 API와의 인터페이스 약속인데, 지금은 프론트엔드 테스트 코드 안에 그 값을 그대로 하드코딩해서 검증하고 있거든요. 만약 백엔드 팀에서 에러 코드를 다른 번호로 변경해 버리면, 프론트엔드 테스트는 여전히 초록불을 띄우고 있지만 실제 프로덕션 환경에서는 에러 처리가 망가져버리는 전형적인 거짓 통과(false negative)가 발생하게 돼요. 프론트엔드(Next.js)와 백엔드(Spring) 두 레포지토리를 잇는 계약 테스트(Contract Test)를 구축하는 것이 가장 확실한 해답이지만, 현재 팀 리소스 상황에서는 도입 비용이 꽤 부담스러워서 일단은 의식적으로 백로그에 남겨둔 상태예요.

그리고 솔직하게 털어놓자면, 이 글에서 다룬 개선 작업의 장기적인 효용은 아직은 가설과 예측의 단계에 있어요. 특정 슬라이스에서 테스트 개수를 90개에서 78개로 최적화하고, 다른 슬라이스에서 가짜 객체로 뒤덮인 테스트를 12개에서 4개로 줄여낸 것은 분명한 실측치이지만, 이 변화가 에이전트의 컨텍스트 낭비와 토큰 병목을 장기적으로 얼마나 극적으로 해소해 줄지는 앞으로 두 달은 더 써봐야 구체적인 데이터가 나올 것 같아요. 유의미한 숫자가 쌓이고 나면 그때 다시 후속 글을 정리해 볼게요. 그때쯤이면 미뤄두었던 백엔드와의 계약 테스트 구멍도 함께 메워진 상태였으면 좋겠네요.
