페이지에서 데이터를 직접 가져오지 마라? 우리 코드를 직접 뜯어보며 확인한 RSC 원칙과 현실적인 제약

React Server Components 원칙을 실제 서비스 코드에 대입해 보며, 잘 지켜진 구조와 불가피했던 예외, 그리고 이를 강제하기 위한 Next.js 16의 cacheComponents까지 살펴본 기록입니다.

들어가며 — "페이지 컴포넌트는 fetch하지 마라"는 글을 읽고 우리 코드를 점검해 본 이유#

얼마 전에 React Server Components(RSC) 설계를 다룬 아티클을 하나 읽었어요. 핵심 주장은 꽤 명확했는데요. 페이지 컴포넌트에서 필요한 데이터를 한 번에 긁어모아 자식 컴포넌트들에게 props로 넘겨주지 말고, 데이터가 필요한 컴포넌트가 자기 데이터를 직접 가져오게(self-fetch) 만들라는 이야기였어요.

말로만 들으면 조금 와닿지 않을 수 있으니 코드로 한번 비교해 볼게요. 글에서 "지양해야 할 패턴"으로 꼽은 구조는 대략 이래요. 페이지 컴포넌트가 화면에 들어갈 데이터를 전부 비동기로 모은 다음, 자식들에게 하나씩 props로 넘겨주는 방식이에요.

// 페이지가 다 가져와서 props로 넘기는 방식
export default async function HomePage() {
  const posts = await getFeed();
  const tags = await getTrendingTags();
  return (
    <>
      <Feed posts={posts} />
      <TrendingTags tags={tags} />
    </>
  );
}

이런 구조가 되면 Feed 컴포넌트는 누군가 바깥에서 posts 데이터를 온전히 조회해 넘겨주지 않으면 혼자서는 아무것도 하지 못해요. 만약 다른 화면에서도 이 Feed UI를 재사용하고 싶다면, 그 페이지 역시 똑같이 posts 데이터를 직접 불러와 넘겨주어야만 하죠. 결국 Feed 컴포넌트가 특정 페이지의 데이터 흐름에 완전히 종속되는 셈이에요.

반면 글에서 권장하는 접근 방식은 정반대예요. Feed 컴포넌트 스스로가 필요한 데이터를 내부에서 직접 비동기로 호출해서 써요.

// 컴포넌트가 자기 데이터를 직접 가져오는 방식
async function Feed() {
  const posts = await getFeed();
  return <ul>{posts.map(/* ... */)}</ul>;
}

export default function HomePage() {
  return (
    <>
      <Feed />
      <TrendingTags />
    </>
  );
}

이렇게 바꾸고 나면 페이지 컴포넌트는 구체적인 데이터 형태를 전혀 몰라도 돼요. 어느 페이지든 그저 <Feed /> 컴포넌트 태그 하나만 가져다 두면 바로 동작하거든요. 페이지는 이제 복잡한 데이터 페칭 책임을 내려놓고, "화면의 어떤 위치에 어떤 블록을 올려둘지"만 결정하는 순수한 레이아웃 배치도 역할에 집중할 수 있게 돼요.

이 내용을 읽으면서 지금 개발 중인 레시피오 프로젝트 코드가 문득 떠올랐어요. '과연 우리 코드는 어느 쪽에 더 가까울까?' 마침 저희 프로젝트가 Next.js 15 App Router 환경에 FSD(Feature-Sliced Design) 아키텍처를 적용해 둔 상태라, 글에서 제시한 기준들을 하나씩 대조해 보기 참 좋은 상태였거든요.

결론부터 짚어보자면, 글에서 내세운 다섯 가지 원칙 중 상당수는 이미 저희 코드베이스에 꽤 잘 녹아들어 있었어요. 특히 핵심인 "컴포넌트가 스스로 데이터를 가져온다"는 원칙은 메인 홈 화면과 레시피 상세 화면 양쪽 모두에서 적극적으로 활용하고 있었고요. 어긋나는 부분은 딱 한 군데뿐이었는데, 검색엔진 최적화(SEO)를 위해 페이지 레벨에서 본문 데이터를 미리 쥐고 있어야만 하는 불가피한 화면이었어요.

하지만 글을 덮고 나서 머릿속에 가장 오래 맴돌았던 생각은 따로 있었어요. '이 구조가 주는 이점이 분명한 건 알겠는데, 과연 무엇이 이 원칙을 흐트러짐 없이 계속 지켜내도록 강제할 수 있을까?' 하는 의문이었죠. 이 글은 그 원칙들을 실제 코드와 비교해 보고, 아키텍처의 강제성에 대한 고민을 따라가 본 과정의 기록이에요.

데이터 주입(Loader)에서 조합(Compose)으로 향하는 Next.js의 흐름#

원문 글에서는 동일한 화면을 구성할 때 선택할 수 있는 데이터 패칭 방식을 크게 세 가지로 나누어 비교해요. 흐름 순서대로 차근차근 짚어볼게요.

첫 번째는 오랫동안 익숙하게 써 온 useEffect 기반의 클라이언트 사이드 패칭이에요. 컴포넌트가 브라우저에 마운트된 직후 자바스크립트로 데이터를 요청하는 방식이죠. 익숙하다는 장점이 있지만 두 가지 고질적인 문제가 따라와요. 서로 다른 컴포넌트가 같은 데이터를 공유해야 할 때마다 부모 컴포넌트로 상태를 끌어올려 props로 줄줄이 내려주어야 하고(흔히 말하는 prop drilling 현상이에요), 컴포넌트가 렌더링되는 위계에 따라 데이터 요청이 순차적으로 꼬리를 무는 네트워크 워터폴(Waterfall)이 발생하기 쉬워요. 앞선 부모의 렌더링과 데이터 패칭이 끝나야 비로소 자식의 요청이 시작되는 구조니까요.

두 번째는 라우트 로더(Route Loader) 패턴이에요. 방금 앞서 살펴본 예시 코드처럼, 페이지 컴포넌트가 Promise.all 등을 활용해 필요한 데이터를 한 번에 묶어서 불러온 다음 자식 컴포넌트들에게 props 형태로 분배해 주는 방식이에요. 요청을 한 시점에 병렬로 처리하니 네트워크 워터폴은 피할 수 있지만, 자식 컴포넌트들이 부모 페이지가 넘겨주는 props에 강하게 결합된다는 한계는 여전히 남아 있어요.

세 번째가 바로 글에서 적극적으로 지향점으로 제시하는 RSC 컴포즈 방식이에요. 각각의 서버 컴포넌트가 자신이 화면에 그릴 데이터를 직접 가져오고, 페이지 컴포넌트는 그 컴포넌트들을 <Suspense>로 감싸 적절한 위치에 조합(Compose)만 해두는 형태예요. 여기서 <Suspense>는 "하위 컴포넌트가 비동기 작업을 마칠 때까지 대체할 로딩 UI(Fallback)를 보여주는 경계선" 역할을 하는데요. 덕분에 각 컴포넌트가 서로의 데이터 응답을 기다리며 멈춰 설 필요 없이, 먼저 준비를 마친 컴포넌트부터 화면에 순차적으로 나타날 수 있어요.

결국 글이 보여주는 방향성은 무척 또렷해요. Next.js의 아키텍처는 페이지 단위에서 데이터를 일괄 취합해 하향식으로 내려보내는 방식에서 벗어나, 데이터 책임을 컴포넌트 단위로 잘게 분산시키고 페이지는 오직 이들을 조립·배치하는 구조를 향해 나아가고 있어요. 실제로 Next.js 16에 도입된 새로운 기능인 cacheComponents 역시 이러한 컴포넌트 단위의 데이터 격리를 전제로 설계되었고요(이 부분은 뒤에서 조금 더 깊이 다뤄볼게요). 그렇다면 지금 저희 프로젝트는 이 흐름 위에서 어느 지점에 서 있을까요?

RSC 5원칙을 실제 우리 프로젝트에 대입해 보기#

아티클에서 제시한 다섯 가지 설계 원칙은 다음과 같아요.

  1. 페이지는 데이터를 직접 가져오지 않고 컴포넌트 배치만 담당한다
  2. 데이터가 필요한 컴포넌트가 자기 데이터를 직접 조회한다
  3. 로딩 스켈레톤 UI는 해당 컴포넌트 바로 옆에 위치시킨다
  4. 로딩 경계(<Suspense>)는 페이지 레벨에서 설계한다
  5. "use client" 지시어는 꼭 필요한 말단 컴포넌트에만 선언한다

원칙을 번호 순서대로 나열하기보다는, 실제 저희 레시피오 코드베이스가 놓인 현실에 맞춰 이미 잘 지키고 있던 부분부터 차례대로 묶어서 정리해 볼게요.

이미 자연스럽게 잘 지키고 있던 세 가지 원칙#

우선 세 번째 원칙인 로딩 스켈레톤의 위치(③)예요. 스켈레톤은 비동기 응답을 기다리는 동안 화면의 깜빡임을 줄이기 위해 띄워두는 회색 뼈대 UI인데요. 저희는 스켈레톤 컴포넌트들을 최상위 공용 폴더에 따로 모아두지 않고, 각 컴포넌트가 속한 FSD 슬라이스의 ui/ 디렉터리 안에 나란히 두고 있어요. 예컨대 RecipeGrid 옆에 RecipeGridSkeleton을 두고, CurationList 옆에 CurationListSkeleton을 함께 위치시키는 식이에요. 이렇게 컴포넌트와 스켈레톤을 한 폴더 안에서 짝지어 관리하면, 본체 컴포넌트의 마크업 구조를 수정할 때 스켈레톤의 형태도 한눈에 확인하며 함께 고칠 수 있어 둘의 레이아웃이 어긋나는 실수를 크게 줄일 수 있어요. 글이 제안한 구조와 완전히 일치하는 방식이죠.

다섯 번째 원칙인 "use client"의 선언 경계(⑤)도 잘 유지되고 있었어요. 파일 상단에 "use client"를 적으면 그 지점부터 하위 트리는 전부 클라이언트 번들에 포함되어 브라우저에서 실행되는데요. 별도로 명시하지 않는 한 기본값은 서버 컴포넌트로 동작해요. 검색엔진 최적화가 중요한 주요 페이지들에서는 이 경계를 철저히 말단 인터랙션 컴포넌트에만 한정해 두었어요. app/page.tsx(메인 홈), recipes/[recipeId]/page.tsx(레시피 상세), curation/page.tsx, search/results/page.tsx 같은 핵심 경로들은 모두 순수 서버 컴포넌트로 유지하고 있고, 사용자의 클릭이나 텍스트 입력 처리가 필요한 영역만 SearchClient 같은 작은 단위의 클라이언트 컴포넌트로 떼어내 조합하고 있어요.

물론 코드베이스 전체를 살펴보면 최상단 첫 줄부터 "use client"가 선언된 페이지 파일도 37개 정도 존재해요. recipe-books, notifications, calendar, admin 화면들이 여기에 해당하는데요. 이건 설계 원칙을 놓쳐서 발생한 문제가 아니라 의도적으로 허용한 예외에 가까워요. 이 페이지들은 로그인 세션 상태나 브라우저 라우팅 상태에 강하게 묶여 있는 순수한 인앱 화면들이라 어차피 클라이언트 사이드에서 동작해야 하고, 검색엔진에 본문 내용을 크롤링시킬 필요도 전혀 없기 때문이에요.

다음으로 컴포넌트 단위의 데이터 조회(②)와 로딩 경계 설계(④)가 맞물려 돌아가는 지점이에요. 레시피 상세 페이지 하단을 보면 "같은 재료 레시피", "이 영상이 검증한 레시피"처럼 연관 콘텐츠를 묶어 보여주는 추천 슬라이드 섹션들이 붙어 있는데요. 이 영역을 렌더링하는 RecipeDetailServerSlides 코드를 보면, 네 개의 슬라이드 컴포넌트를 각각 별도의 <Suspense> 경계로 감싸두고 있어요.

<Suspense fallback={<SlideFallback />}>
  <SameIngredientServerSlide recipeId={recipeId} locale={locale} />
</Suspense>

이렇게 각 슬라이드를 <Suspense>로 개별 격리해 둔 덕분에, 네 개의 슬라이드는 느린 응답에 발목 잡히지 않고 각자 서버 작업이 끝나는 순서대로 화면에 스트리밍되어 나타나요(④). 그리고 이 SameIngredientServerSlide 컴포넌트는 부모인 페이지로부터 props로 데이터를 넘겨받지 않고, 자신이 렌더링할 데이터를 컴포넌트 내부에서 직접 조회해 와요(②).

const { ingredientName, content, fetchFailed } = await getSameIngredientOnServer(recipeId, locale);

이처럼 서버 환경에서 독립적으로 데이터를 불러오는 슬라이드 컴포넌트가 적지 않아요. 실제 저희 api.server.ts 모듈을 살펴보면 getSeasonalPopularOnServer, getYoutubeVerifiedOnServer, getCountryPopularOnServer처럼 슬라이드 컴포넌트 전용으로 분리된 비동기 함수들이 준비되어 있고, 메인 홈 화면의 슬라이드 다섯 개와 상세 화면의 슬라이드 네 개가 모두 이 패턴으로 동작하고 있어요. 결국 글에서 가장 강하게 역설했던 "컴포넌트가 자기 데이터를 직접 가져온다"는 원칙은, 저희가 구현하지 못하고 있던 이상향이 아니라 이미 프로덕션 코드 곳곳에서 자연스럽게 써오던 패턴이었던 셈이에요.

유일하게 페이지가 직접 데이터를 가져왔던 이유와 예외 처리#

그렇다면 저희 코드가 두 번째 원칙을 모든 영역에서 철저하게 지키고 있을까요? 그렇지는 않아요. 딱 한 가지 종류의 데이터에 한해서는 여전히 페이지 컴포넌트가 직접 데이터를 가져와 자식에게 props로 넘겨주는 방식을 유지하고 있어요. 레시피 상세 화면의 본문 데이터가 대표적인 사례인데요. 실제 recipes/[recipeId]/page.tsx 파일은 다음과 같은 구조로 작성되어 있어요.

const staticRecipe = await getStaticrecipionServer(recipeId);
// ...
return <RecipeDetailView recipe={staticRecipe} bottomSlides={/* ... */} />;

원문의 엄격한 잣대로만 평가하자면 이는 분명한 안티패턴에 해당해요. 페이지 컴포넌트가 본문 데이터를 직접 await로 가져온 뒤 하위 뷰 컴포넌트에 props로 주입하고 있으니까요. 하지만 여기에는 현실적인 아키텍처 제약 때문에 타협할 수밖에 없었던 명확한 기술적 이유가 있어요.

이 레시피 상세 데이터는 화면 본문을 그리는 용도로만 쓰이는 게 아니거든요. 검색엔진 결과에 노출할 페이지 제목과 설명을 동적으로 생성하는 generateMetadata 함수에서도 이 데이터를 반드시 참조해야 하고, 구글 검색엔진 크롤러가 읽어갈 구조화 데이터(JSON-LD) 스크립트를 조립할 때도 똑같은 레시피 데이터가 필요해요. 문제는 이 메타데이터들이 실제 React 컴포넌트 트리가 렌더링되기 전에, 페이지 수명 주기 상단에서 먼저 완성되어야 한다는 점이에요. 결국 검색엔진 최적화를 챙기려면 페이지 레벨에서 레시피 원본 데이터를 최소 한 번은 직접 손에 쥘 수밖에 없는 구조인 거죠. 원문 글이 가볍게 지나쳤던 현실적인 제약이 바로 이 지점이에요. 서버 사이드 메타데이터 생성이 필수적인 프로덕션 환경에서는 "페이지 컴포넌트는 데이터의 형태를 몰라야 한다"는 이상을 있는 그대로 적용하기가 어려워요.

이 지점에서 흔히 들 수 있는 의문이 하나 있어요. 페이지 컴포넌트 본문에서 한 번 호출하고 generateMetadata에서 또 호출하면, 네트워크 비용을 들여 같은 API를 두 번씩 중복 요청하게 되는 것 아니냐는 걱정인데요. 실제로는 그렇지 않아요. 이 조회 로직은 React의 cache()를 거치지 않고 웹 표준 네이티브 fetch를 그대로 사용하는데요. Next.js 프레임워크 차원에서 단일 렌더링 패스 동안 동일한 URL과 옵션으로 들어오는 fetch 요청을 자동으로 중복 제거(Request Memoization)해 단 한 번의 네트워크 요청으로 합쳐주거든요. 따라서 두 함수에서 각각 호출하더라도 실제 백엔드로 나가는 요청은 단 한 번으로 최적화돼요. (React의 cache() 래핑이 별도로 필요한 상황은 네이티브 fetch가 아닌 데이터베이스 드라이버를 직접 호출하거나 ORM을 사용하는 경우에 한해요.)

재밌는 사실은 메인 홈 화면(app/page.tsx)을 열어보면 이 두 가지 패러다임이 한 파일 안에 나란히 공존하고 있다는 점이에요. 화면 상단의 인기 레시피 및 가성비 레시피 영역은 페이지 레벨에서 Promise.all로 함께 패칭해 자식 컴포넌트에 props로 내려주고 있는 반면, 화면 하단의 디스커버리 슬라이드 다섯 개는 각 컴포넌트가 독립적으로 자기 데이터를 불러오도록 분리되어 있거든요. 이렇게 한 화면 안에서 접근 방식이 나뉜 이유 역시 분명해요. 상단 영역의 데이터는 검색 로봇을 위한 오픈그래프 메타데이터 생성에 활용되는 반면, 하단 슬라이드들은 오직 화면 표시만을 목적으로 하기 때문이에요. 저희 팀이 어떤 기준으로 원칙과 실용성을 절충했는지가 단일 파일 안에 고스란히 묻어 있는 셈이죠.

글에서 다루지 않은 무한 스크롤 하이드레이션과 아직 남은 숙제#

원문에서 다룬 단순 컴포넌트 데이터 패칭 모델만으로는 쉽게 풀어내기 힘든 현실적인 화면들도 있어요. 대표적인 예가 큐레이션 목록이나 검색 결과처럼 사용자가 화면을 아래로 내릴 때마다 다음 페이지 데이터가 이어 붙어야 하는 무한 스크롤(Infinite Scroll) 뷰예요. 서버 컴포넌트는 요청 시점에 HTML을 한 번 렌더링해 스트리밍하고 나면 브라우저 상에서 동작을 멈추기 때문에, "사용자의 스크롤 이벤트에 반응해 2페이지, 3페이지를 점진적으로 추가 호출하는" 인터랙션을 자체적으로 처리할 수 없어요. 그래서 이런 화면에서는 서버 환경에서 첫 번째 페이지 데이터만 미리 페칭해 둔 뒤, 브라우저 마운트 시점부터는 클라이언트 측의 TanStack Query가 바통을 이어받아 처리하는 하이브리드 방식을 채택해요.

이렇게 서버가 미리 준비한 초기 상태를 클라이언트 캐시로 온전히 넘겨주는 과정을 하이드레이션(Hydration)이라고 불러요. 구체적인 코드 흐름을 보면, 서버 환경에서 prefetchInfiniteQuery를 통해 첫 페이지 분량의 데이터를 미리 가져온 뒤 이를 dehydrate 함수로 직렬화해요. 그리고 이 상태를 <HydrationBoundary> 컴포넌트로 감싸 클라이언트에 안전하게 전달하죠. 이렇게 구성해 두면 클라이언트의 쿼리 훅은 첫 페이지를 서버에 다시 요청하지 않고 캐시에서 즉시 꺼내 렌더링한 뒤, 사용자가 바닥에 도달했을 때부터 자연스럽게 두 번째 페이지 요청을 발생시켜요. 원문이 설명한 순수 self-fetch 서버 컴포넌트와는 결이 다른 패턴이지만, 이것은 설계 수준이 뒤처져서가 아니라 무한 스크롤이라는 전혀 다른 사용자 경험을 해결하기 위한 필연적인 구조예요.

다만 이 영역에서도 최근 의미 있는 구조 개선 작업을 하나 진행했어요. 검색 결과 페이지의 경우 원래 이 하이드레이션 초기화 로직 전체를 페이지 컴포넌트가 직접 떠안고 있었거든요. 페이지 컴포넌트 내부에서 첫 페이지를 prefetch하고, 그 응답 객체로부터 다음 페이지 URL과 구조화 데이터(JSON-LD)까지 직접 연산해 하위로 내려보내던 형태였어요. 저희는 이 무거운 책임들을 SearchResultsData라는 별도의 독립 컴포넌트로 완전히 격리해 분리해 내고, 바깥을 <Suspense>로 감싸주었어요. 하이드레이션 파이프라인 자체는 유지하되, 데이터를 다루는 주체를 페이지 레벨에서 하위 컴포넌트 내부로 한 단계 끌어내린 거예요. 덕분에 검색 결과 페이지 컴포넌트는 이제 검색 필터의 외곽 뼈대와 로딩 경계선만 선언하는 레이아웃 본연의 역할로 돌아갔고, 구체적인 결과 데이터 패칭은 내부 컴포넌트가 스스로 전담하게 되었어요. 무한 스크롤 인터랙션의 한계상 완전한 순수 self-fetch 서버 컴포넌트로 갈 수는 없더라도, "페이지는 오직 배치만 담당한다"는 아키텍처 원칙에 한 걸음 더 가까워진 셈이에요. (참고로 큐레이션 페이지는 아직 페이지 컴포넌트가 직접 prefetch를 수행하는 이전 방식에 머물러 있어요.)

로딩 상태를 처리하는 전략 역시 라우트가 가진 성격에 맞춰 두 가지 방식을 영리하게 조합해 쓰고 있어요. Next.js App Router에는 특정 라우트 세그먼트 전체에 일괄적으로 로딩 화면을 덧씌워주는 loading.tsx 규약이 마련되어 있는데요. /search나 /search/results처럼 서버에서 데이터 조회를 마치기 전까지 화면 전환을 지연시키지 않고 스트리밍을 태워야 하는 검색 진입 경로들에는 이 loading.tsx를 적극적으로 배치해 두었어요. 사용자가 링크를 클릭해 넘어가는 순간 이전 화면에 멈춰 서 있는 느낌을 받지 않고, 즉각적으로 스켈레톤 레이아웃으로 전환되도록 만들기 위함이에요. 반면 레시피 상세 화면의 하단 슬라이드들처럼 한 화면 안에서 개별 블록들이 점진적으로 채워져야 하는 영역에는 컴포넌트 단위로 <Suspense> 경계를 쪼개어 배치했어요. 어떤 블록이 먼저 렌더링되고 어떤 영역이 나중에 채워질지를 컴포넌트 수준에서 훨씬 미세하게 제어하기 위해서죠.

물론 아직 미처 손대지 못한 아쉬운 영역도 솔직하게 남아 있어요. 앞서 메인 홈 화면의 디스커버리 슬라이드 다섯 개가 자기 데이터를 스스로 가져오도록 잘 격리되어 있다고 말씀드렸는데요(원칙 ②는 달성). 하지만 상세 화면과 달리 이 슬라이드들은 상위에서 <Suspense> 경계로 감싸져 있지 않은 상태예요(원칙 ④의 누락). 서버 컴포넌트가 <Suspense> 경계 없이 비동기 데이터를 직접 호출하게 되면, 해당 컴포넌트의 데이터 조회가 완전히 끝날 때까지 부모 페이지 전체의 렌더링 스트림이 함께 블로킹되는 부작용이 생겨요. 상세 화면에서는 슬라이드마다 경계를 꼼꼼히 쳐두어 먼저 준비된 콘텐츠부터 즉각 띄워주고 있지만, 홈 화면은 아직 그 구조를 갖추지 못해 반쪽짜리 최적화에 머물러 있는 상태예요.

좋은 아키텍처를 유지하려면 사람의 의지가 아닌 강제 장치가 필요하다#

지금까지 읽은 글의 내용과 저희 프로젝트의 실제 코드베이스를 꼼꼼히 대조해 보았어요. 이제 서두에서 잠시 미뤄두었던 본질적인 고민으로 돌아와 볼게요. 이 컴포넌트 중심의 아키텍처가 장기적으로 유지보수하기에 좋은 구조라는 점에는 충분히 동의할 수 있어요. 그렇다면 무엇이 개발자들로 하여금 이 원칙을 흐트러짐 없이 계속 지켜나가도록 만들어 줄 수 있을까요?

새로운 동료가 팀에 합류하거나, 혹은 기존 팀원이라도 일정에 쫓겨 바쁜 날에는 페이지 컴포넌트 최상단에 무심코 await fetch() 한 줄을 적어 내려갈 수 있잖아요. 시스템 차원에서 이를 확실히 차단해 주는 안전장치가 없다면, 아무리 좋은 아키텍처 원칙이라도 문서 속의 이상론으로 흩어지고 코드는 점차 과거의 복잡한 스파게티 형태로 회귀하기 마련이에요. 그래서 규칙을 어겼을 때 물리적으로 작업을 멈춰 세우는 '강제 수단'이 반드시 필요해요. 처음에는 해결책이 무척 단순할 거라고 생각했어요. 저희 프로젝트가 FSD 아키텍처를 쓰고 있고 ESLint 규칙도 엄격하게 적용해 둔 편이니, 린트 룰 하나만 추가하면 깔끔하게 해결될 문제라고 여겼거든요. 하지만 구체적으로 조사해 보니 현실은 전혀 달랐어요.

린트 규칙과 FSD 아키텍처로는 페이지의 데이터 조회를 막지 못하는 이유#

우선 정적 분석 도구인 린트(ESLint) 생태계부터 뒤져보았어요. "페이지 컴포넌트 파일 안에서 비동기 데이터 패칭 함수를 직접 호출하면 에러를 발생시킨다" 같은 규칙이 존재하는지 찾아보았지만, 그런 룰은 존재하지 않았어요. React Server Components 환경에서 가장 널리 쓰이는 eslint-plugin-react-server-components 플러그인이 수행하는 검사는 "클라이언트 전용 훅이나 브라우저 API를 쓰면서 상단에 "use client"를 선언하지 않은 파일"을 잡아내는 게 전부예요. Next.js 공식 ESLint 플러그인 역시 next/image나 스크립트 태그, <head> 메타데이터의 올바른 사용법을 강제하는 수준에 머물러 있고요. "어느 레이어의 컴포넌트가 데이터 패칭을 주도하는가"라는 소프트웨어 설계의 역할과 책임을 분석해 주는 린트 규칙은 어디에도 없었어요.

'그렇다면 커스텀 AST 린트 룰을 직접 작성하면 되지 않을까?' 싶을 수도 있지만, 이 역시 기술적인 한계가 뚜렷해요. 린트는 코드의 문법 구조(AST)와 텍스트 패턴만 들여다볼 뿐, 런타임에 그 코드가 실제로 어떤 성격의 작업을 수행하는지 그 의미론(Semantics)까지 온전히 이해하지는 못하거든요. 페이지 파일 안에 await 키워드가 등장했다고 해서, 이것이 외부 네트워크를 찌르는 데이터 패칭인지 아니면 단순히 URL 파라미터를 읽어오는 안전한 await params 구문인지 린트 수준에서는 명확히 분간해 내기 어려워요. 결국 함수 이름이 get이나 fetch로 시작하는 패턴만 골라 에러를 띄우는 식의 취약한 네이밍 규칙에 의존하게 되는데, 이런 규칙은 작은 예외 상황에서도 쉽게 무력화되거나 잘못된 경고(False Positive)를 남발하기 십상이에요.

그렇다면 저희가 공들여 구축해 둔 FSD(Feature-Sliced Design) 아키텍처는 이를 막아줄 수 있을까요? 결론부터 말하자면 FSD 역시 이 흐름을 제어하지 못해요. 저희 프로젝트의 eslint.config.mjs에 선언된 fsd-import 린트 규칙을 뜯어보면, 이 룰이 감시하는 대상은 전적으로 파일 간의 import 구문 경로에 국한되어 있어요. 예를 들어 하위 레이어인 shared 모듈이 상위 레이어인 features를 역방향으로 참조하거나, 같은 슬라이스 계층끼리 교차 의존성을 만들어 아키텍처 계층을 무너뜨리는 행위를 엄격히 차단해 줄 뿐이죠. 즉 "어느 위치의 파일이 어느 모듈을 파일 시스템 상에서 가져올 수 있는가"라는 의존성 방향만을 검사하는 도구예요.

컴포넌트 함수 내부에서 실행되는 await fetch() 같은 구체적인 비동기 호출 행위는 애초에 FSD 린트 규칙의 검사 영역 밖이에요. FSD 규칙은 컴파일 타임의 모듈 참조 관계만을 바라볼 뿐, 런타임에 어떤 위치에서 데이터 요청이 촉발되는가에는 관여하지 않거든요. 둘은 아예 바라보는 차원이 다른 도구이기 때문에, fsd-import 린트 설정을 아무리 엄격하게 조이더라도 page.tsx 안에서 await getStaticrecipionServer() 같은 데이터 조회 함수를 직접 실행하는 코드는 아무런 제지 없이 유유히 통과해 버려요.

규칙 위반 시 빌드를 실패시키는 유일한 장치, Next.js 16 cacheComponents#

이러한 설계 원칙을 개발자의 주관적인 판단에 기대지 않고 물리적으로 강제할 수 있는 유일한 수단은 Next.js 16에 새로 추가된 cacheComponents 플래그뿐이었어요. 이 옵션을 활성화하면 런타임과 빌드 파이프라인 전반에 아주 엄격한 단 하나의 규칙이 적용돼요. 바로 매 요청마다 동적으로 변경되는 캐시되지 않은 데이터(Uncached data)를 <Suspense> 경계 바깥에서 읽어 들이려고 시도할 경우 컴파일러가 빌드를 즉각 중단시키는 규칙이에요. 이때 터져 나오는 에러 메시지도 "Uncached data was accessed outside of <Suspense>"(캐시되지 않은 동적 데이터가 Suspense 경계 바깥에서 접근되었습니다)라고 아주 직관적으로 원인을 짚어줘요. 로컬 개발 환경에서 즉시 런타임 에러로 피드백을 줄 뿐만 아니라, CI/CD 파이프라인에서 프로덕션 배포를 위해 next build 명령을 수행할 때도 빌드가 강제로 터지면서 배포 자체가 원천 차단돼요.

이 빌드 에러를 정상적으로 통과하기 위해서는 코드베이스를 다음의 두 가지 선택지 중 하나에 맞추어 수정해야만 해요. 다루려는 데이터가 요청마다 매번 바뀌지 않는 정적 성격의 리소스라면(예를 들어 며칠에 한 번 갱신되는 인기 레시피 목록 같은 데이터라면) 함수에 'use cache' 지시어를 명시해 빌드 시점에 안전하게 캐싱되도록 처리해야 하고요. 반대로 사용자의 실시간 상태나 매 요청마다 새롭게 바뀌어야 하는 동적 데이터라면 해당 데이터를 읽는 컴포넌트 상위에 반드시 <Suspense> 경계를 둘러주어야 해요.

이 지점이 일반적인 린트 정적 분석 도구와 결정적으로 다른 부분이에요. 린트는 코드 스타일 가이드를 제안하며 경고를 띄우는 데 그치기 때문에 무시하고 넘어가도 애플리케이션 자체는 어떻게든 배포되어 돌아가지만, cacheComponents 플래그는 조건을 만족하지 않으면 아예 프로덕션 빌드 생성을 거부해 버리기 때문에 코드를 올바른 구조로 수정하지 않고서는 배포 자체가 불가능해져요. 한 가지 정확히 짚고 넘어갈 점은, 이 플래그가 "페이지 컴포넌트에서는 fetch를 쓰지 마라"는 규칙을 문자 그대로 감시하는 도구는 아니라는 사실이에요. 엔진이 강제하는 본질적인 규칙은 "동적으로 변화하는 데이터를 읽으려면 그 상위에 반드시 <Suspense> 로딩 경계가 존재해야 한다"는 제약이고요. 페이지 컴포넌트가 세부 데이터를 직접 쥐지 않고 하위 컴포넌트로 데이터 페칭 책임을 넘긴 뒤 페이지는 이들을 <Suspense>로 감싸는 구조는, 이 엄격한 렌더링 제약을 충족하는 과정에서 자연스럽게 도출되는 아키텍처적 결과물인 셈이에요.

우리 프로젝트에서 아직 도입하지 못한 배경과 현재 구조를 지켜내는 방식#

그렇다면 저희 레시피오 프로젝트에서도 이 강력한 cacheComponents 기능을 지금 즉시 켜서 적용했을까요? 아쉽게도 그러지 못했어요. 크게 두 가지 현실적인 기술적 이유 때문이에요.

첫 번째로, 현재 저희 프로덕션 환경은 Next.js 15.3 버전을 기반으로 구동되고 있어 cacheComponents 기능 자체가 프레임워크에 존재하지 않아요. 이 강력한 제약 기능은 Next.js 16 메이저 버전부터 새롭게 도입된 기능이거든요. 두 번째로, 설령 프레임워크 버전을 16으로 올린다 하더라도 이 플래그를 프로덕션 전체에 당장 활성화하기는 무척 까다로워요. 앞서 살펴보았듯 저희 서비스의 핵심 페이지들 중 상당수가 클라이언트 쿼리 상태를 복원하는 하이드레이션 파이프라인이나, 서버 사이드 동적 메타데이터 생성 로직에 깊게 의존하고 있거든요. 그런데 cacheComponents는 "Suspense 경계 바깥의 모든 정적 레이아웃 영역은 빌드 시점에 완벽하게 사전 렌더링되어 준비되어야 한다"는 매우 엄격한 멘탈 모델을 요구하기 때문에, 이 플래그를 안정적으로 통과시키려면 기존 페이지들의 데이터 수명 주기를 전면적으로 재설계해야만 해요.

결국 지금 시점에서 저희가 마주한 솔직한 현실은 이거예요. 현재 저희 코드베이스에서 이 건강한 RSC 아키텍처를 지탱해 주고 있는 것은 고도화된 정적 분석 린트도, 프레임워크 엔진의 강제 제약도 아니에요. 순수하게 개발팀 내부의 컨벤션에 대한 공감대와 꼼꼼한 코드 리뷰 문화에 의존해 버텨내고 있어요. 새로운 추천 슬라이드를 만들 때는 습관적으로 컴포넌트 내부에서 자기 데이터를 직접 호출하도록 격리하고, FSD 슬라이스 구조가 유도하는 파일 배치 패턴을 따르며, 풀 리퀘스트(PR) 리뷰 과정에서 "이 비동기 조회 로직은 페이지에서 한 번에 부르지 말고 하위 슬라이드 컴포넌트 안으로 밀어 넣죠"라고 서로 피드백을 건네는 동료 간의 소통이 유일한 방어선인 셈이죠. 향후 시스템을 Next.js 16으로 업그레이드하고 cacheComponents를 도입하게 된다면, 메타데이터 의존성이 없는 화면 외곽의 독립 위젯들(실시간 트렌딩이나 개인화 추천 섹션 등)부터 차근차근 <Suspense> 경계를 씌워 단계적으로 적용해 나가는 방식이 가장 현실적인 첫걸음이 될 거라고 생각해요.

마치며 — 원칙의 지향점과 현실적인 비즈니스 제약 사이의 균형#

원문 글의 주장들을 저희 프로덕션 코드에 하나씩 대입해 보며 최종적으로 든 생각은, 지금 저희의 아키텍처가 이상적인 이론을 맹목적으로 복제한 결과물도 아니지만 그렇다고 원칙에서 완전히 벗어난 누더기 코드도 아니라는 점이었어요. 검색엔진 최적화나 복잡한 사용자 인터랙션 같은 실제 비즈니스 제약 조건들이 허락하는 테두리 안에서, 원칙이 주는 장점을 최대한 흡수해 타협점을 찾아낸 현실적인 결과물이었던 거죠. 컴포넌트가 스스로 데이터를 가져와 결합도를 낮추는 핵심 설계는 충실히 계승하되, 서버 메타데이터 생성이 절실한 영역에서만 페이지가 데이터를 쥐도록 유연한 예외를 인정해 준 것처럼요.

앞으로 풀어나가야 할 기술적인 숙제는 크게 두 가지로 정리해 볼 수 있을 것 같아요. 우선 홈 화면의 디스커버리 슬라이드 영역에 누락되어 있던 <Suspense> 경계를 꼼꼼히 채워 넣어 독립적인 스트리밍 최적화를 완성하는 작업이고요. 다음으로는 언젠가 프레임워크 버전을 Next.js 16으로 올리는 시점에, 부가 기능 위젯들부터 차근차근 cacheComponents의 빌드 강제성을 실험해 보며 시스템적인 안전장치를 한 겹씩 덧씌워 나가는 일이에요. 프레임워크가 아키텍처를 스스로 강제해 주는 그날이 오기 전까지는, 결국 리뷰 과정에서 팀원들과 좋은 질문을 주고받으며 코드 한 줄의 위치를 함께 고민해 나가는 정성이 이 건강한 구조를 지켜내는 가장 단단한 힘이 되어줄 테니까요.
