페이지는 fetch하지 마라 — 라는 글을 들고 우리 코드를 뜯어봤다

RSC 5원칙을 레시피오 코드에 하나씩 대보고, 지킨 것과 한 군데 예외, 그리고 이 구조를 강제할 수단이 무엇인지 따라간 기록.

들어가며 — "페이지는 fetch하지 마라"를 읽다가 우리 코드가 떠올랐다#

며칠 전에 React Server Components(RSC) 구조를 다룬 글을 하나 읽었어요. 주장은 짧았어요. 페이지 컴포넌트에서 데이터를 한꺼번에 가져와 자식들한테 넘기지 말고, 데이터가 필요한 컴포넌트가 자기 데이터를 직접 가져오게 하라는 거예요.

말로만 들으면 추상적이니 코드로 볼게요. 글이 "이렇게 하지 마라"고 한 방식은 이래요. 페이지가 화면에 필요한 데이터를 전부 모은 다음, 자식한테 props로 넘겨줘요.

// 페이지가 다 가져와서 props로 넘기는 방식
export default async function HomePage() {
  const posts = await getFeed();
  const tags = await getTrendingTags();
  return (
    <>
      <Feed posts={posts} />
      <TrendingTags tags={tags} />
    </>
  );
}

이러면 Feed는 누가 posts를 만들어 넘겨줘야만 동작하는 컴포넌트가 돼요. 다른 페이지에서 Feed를 쓰고 싶으면 그 페이지도 똑같이 posts를 만들어 넘겨야 하고요. Feed가 페이지에 매여버리는 거죠.

글이 권하는 방식은 반대예요. Feed가 자기 데이터를 안에서 직접 가져와요.

// 컴포넌트가 자기 데이터를 직접 가져오는 방식
async function Feed() {
  const posts = await getFeed();
  return <ul>{posts.map(/* ... */)}</ul>;
}

export default function HomePage() {
  return (
    <>
      <Feed />
      <TrendingTags />
    </>
  );
}

이제 페이지는 데이터를 몰라요. <Feed /> 한 줄만 쓰면 어느 페이지에든 갖다 붙일 수 있고요. 페이지는 "무엇을 어디에 놓을지"만 정하는 배치도 역할만 하게 돼요.

이 글을 읽으면서 우리 레시피오 코드가 떠올랐어요. 우리는 어느 쪽일까? 마침 우리는 Next.js 15 App Router에 FSD(Feature-Sliced Design)로 짜여 있어서, 글의 주장을 우리 코드에 하나씩 대보기 좋았어요.

결론부터 말하면, 글이 내세운 원칙 다섯 개 중 대부분은 이미 우리 코드에 들어 있었어요. 특히 방금 본 "컴포넌트가 자기 데이터를 직접 가져온다"는 핵심은 홈에서도 상세에서도 쓰고 있었고요. 어긋나는 건 딱 한 군데였어요. 레시피 본문처럼, 검색 결과에 노출하려고 페이지가 데이터를 미리 손에 쥐어야만 하는 경우였죠.

그런데 글을 덮고 나서 제일 오래 남은 건 다른 질문이었어요. 이 구조가 좋은 건 알겠는데, 무엇이 이걸 계속 지키게 만들까? 이 글은 그 대조, 그리고 그 질문을 따라간 기록이에요.

loader에서 compose로 — 글이 그리는 Next의 방향#

글은 같은 화면을 만드는 세 가지 방식을 나란히 비교해요. 하나씩 볼게요.

첫 번째는 useEffect 방식이에요. 컴포넌트가 화면에 그려진 뒤, 클라이언트에서 데이터를 가져와요. 익숙하지만 두 가지가 걸려요. 컴포넌트끼리 같은 데이터를 써야 하면 그 데이터를 공통 부모로 끌어올려서 나눠줘야 하고(흔히 prop drilling이라 부르는 그거예요), 데이터 요청이 컴포넌트가 그려지는 순서대로 줄줄이 일어나서 느려져요. 앞 요청이 끝나야 다음 요청이 시작되는 식이죠. 이걸 워터폴이라고 해요.

두 번째는 라우트 로더예요. 아까 들어가며에서 본 그 방식이에요. 페이지가 Promise.all로 필요한 데이터를 한 번에 다 가져온 뒤 props로 자식한테 뿌려요. 요청을 한꺼번에 보내니 워터폴은 없어요. 대신 자식 컴포넌트가 페이지에 매이는 문제가 남죠.

세 번째가 글이 미는 RSC 방식이에요. 각 서버 컴포넌트가 자기 데이터를 직접 가져오고, 페이지는 그 컴포넌트들을 <Suspense>로 감싸 배치만 해요. <Suspense>는 "이 안의 컴포넌트가 데이터를 가져오는 동안엔 잠깐 로딩 UI를 대신 보여줘"라고 표시하는 경계예요. 그래서 컴포넌트마다 따로 로딩되고, 먼저 준비된 것부터 화면에 떠요.

그래서 글이 그리는 그림은 분명해요. Next는 페이지에서 데이터를 다 모아 내려보내는 구조가 아니라, 데이터를 컴포넌트별로 쪼개서 페이지는 배치만 하면 되는 구조로 가고 있어요. Next 16의 새 기능 cacheComponents도 이 방향을 전제로 만들어졌고요(이건 뒤에서 따로 다룰게요). 그럼 우리 코드는 이 방향의 어디쯤 있을까요?

우리 코드에 5원칙을 하나씩 대보면#

글의 다섯 원칙은 이거예요.

  1. 페이지는 데이터를 가져오지 않고 배치만 한다
  2. 데이터가 필요한 컴포넌트가 자기 데이터를 직접 가져온다
  3. 로딩 스켈레톤은 그 컴포넌트 바로 옆에 둔다
  4. 로딩 경계(<Suspense>)는 페이지에서 설계한다
  5. "use client"는 꼭 필요한 말단 컴포넌트에만 붙인다

원칙 번호 순서대로 가기보다, 우리 코드가 실제로 어디 서 있는지를 기준으로 묶어볼게요. 잘 지킨 것부터요.

거의 다 지키고 있던 것#

스켈레톤(③)부터요. 스켈레톤은 데이터가 오기 전에 잠깐 보여주는 회색 뼈대 UI예요. 우리는 이걸 공용 폴더에 모으지 않고, 그 컴포넌트가 사는 슬라이스의 ui/ 폴더에 같이 둬요. RecipeGrid 옆에 RecipeGridSkeleton, CurationList 옆에 CurationListSkeleton 하는 식으로요. 이렇게 두면 컴포넌트를 고칠 때 스켈레톤도 같은 폴더에서 같이 눈에 들어와서, 둘이 따로 노는 일이 줄어요. 글이 말한 그대로예요.

"use client" 경계(⑤)도 보죠. "use client"는 그 파일부터 아래로 전부 클라이언트에서 돌리겠다는 선언이에요. 안 붙이면 기본이 서버 컴포넌트고요. 검색 노출이 중요한 페이지에선 이걸 말단에만 붙여요. app/page.tsx(홈), recipes/[recipeId]/page.tsx(레시피 상세), curation/page.tsx, search/results/page.tsx는 전부 서버 컴포넌트로 두고, 클릭이나 입력 같은 상호작용이 필요한 부분만 SearchClient 같은 작은 클라이언트 컴포넌트로 떼어내요.

물론 파일 첫 줄부터 "use client"인 페이지도 37개 있어요. recipe-books, notifications, calendar, admin 같은 화면이에요. 근데 이건 원칙을 어긴 게 아니라 일부러 둔 예외예요. 이런 화면은 로그인 상태나 라우터에 의존하는 순수 앱 화면이라 어차피 클라이언트로 돌아가야 하고, 구글에 노출될 필요도 없거든요.

이제 ④와 ②가 같이 보이는 곳이에요. 레시피 상세 페이지 아래쪽엔 "같은 재료 레시피", "이 영상이 검증한 레시피" 같은 슬라이드가 붙어요. 이걸 만드는 RecipeDetailServerSlides를 보면, 슬라이드 네 개를 각각 <Suspense>로 감싸요.

<Suspense fallback={<SlideFallback />}>
  <SameIngredientServerSlide recipeId={recipeId} locale={locale} />
</Suspense>

<Suspense>로 감싼 덕분에 네 슬라이드가 서로를 안 기다리고 각자 준비되는 대로 떠요(④). 그리고 저 SameIngredientServerSlide는 props로 데이터를 받지 않아요. 자기가 직접 가져와요(②).

const { ingredientName, content, fetchFailed } = await getSameIngredientOnServer(recipeId, locale);

이렇게 자기 데이터를 직접 가져오는 서버 슬라이드가 한둘이 아니에요. api.server.ts에 getSeasonalPopularOnServer, getYoutubeVerifiedOnServer, getCountryPopularOnServer처럼 슬라이드 전용 함수가 줄줄이 있고, 홈 화면 슬라이드 다섯 개랑 상세 슬라이드 네 개가 전부 이 방식이에요. 글이 가장 강조한 "컴포넌트가 자기 데이터를 직접 가져온다"는 원칙은, 우리가 못 하던 게 아니라 이미 곳곳에서 쓰던 패턴이었어요.

딱 한 군데 예외, 그리고 왜#

그럼 우리는 ②를 완벽히 지키느냐. 그건 아니에요. 딱 한 종류의 데이터에서만 페이지가 직접 가져와 props로 내려요. 레시피 본문이 대표적이에요. recipes/[recipeId]/page.tsx는 이렇게 생겼어요.

const staticRecipe = await getStaticrecipionServer(recipeId);
// ...
return <RecipeDetailView recipe={staticRecipe} bottomSlides={/* ... */} />;

글의 기준으론 안티패턴이에요. 페이지가 본문 데이터를 직접 가져와 props로 내리고 있으니까요. 근데 여기엔 안 그럴 수 없는 이유가 있어요.

같은 레시피 데이터를 본문만 쓰는 게 아니거든요. 검색엔진에 보여줄 페이지 제목·설명을 만드는 generateMetadata도 이 레시피를 쓰고, 구글이 읽어가는 구조화 데이터(JSON-LD)도 같은 레시피를 써요. 그런데 이 메타데이터들은 컴포넌트가 그려지기 전에, 페이지 단에서 먼저 만들어져야 해요. 그러니 페이지가 레시피 데이터를 한 번은 손에 쥘 수밖에 없어요. 이게 글이 가볍게 넘어간 부분이에요. 검색 노출 때문에 서버에서 메타데이터를 만들어야 하는 페이지는, "페이지는 데이터를 모른다"는 이상을 그대로 따를 수가 없어요.

여기서 흔한 걱정 하나. 페이지에서 한 번 가져오고 generateMetadata에서 또 가져오면, 같은 데이터를 두 번 부르는 거 아니냐고요. 아니에요. 이 함수는 React의 cache()를 쓰는 게 아니라 그냥 네이티브 fetch를 쓰는데, Next는 한 번 화면을 그리는 동안 똑같은 주소·옵션의 fetch가 여러 번 불리면 알아서 한 번으로 합쳐줘요. 그래서 두 군데서 불러도 실제 네트워크 요청은 한 번이에요. (cache()를 따로 써야 하는 건 fetch가 아닌 데이터, 예를 들어 DB를 직접 부르는 경우예요.)

재밌는 건 홈(app/page.tsx)이에요. 한 파일 안에 두 방식이 섞여 있거든요. 위쪽 인기·저가 레시피는 페이지가 Promise.all로 가져와 props로 내리고, 아래쪽 디스커버리 슬라이드 다섯 개는 각자 자기 데이터를 가져와요. 왜 갈렸냐면, 위쪽은 검색 노출용 메타데이터에 쓰이는 데이터고 아래쪽은 아니거든요. 우리가 어떤 기준으로 둘을 나누는지가 한 파일에 그대로 드러나요.

글이 안 다룬, 우리가 다르게 풀거나 아직 덜 한 곳#

글의 방식만으로는 안 풀리는 화면도 있어요. 큐레이션이나 검색 결과처럼, 스크롤하면 다음 페이지가 계속 붙는 무한스크롤 화면이에요. 서버 컴포넌트는 한 번 그리고 끝이라 "스크롤할 때마다 더 가져오기"를 못 해요. 그래서 여기선 서버에서 첫 페이지만 미리 가져와 두고, 그 다음부터는 클라이언트의 TanStack Query가 이어받아요.

이 "서버가 미리 가져온 데이터를 클라이언트로 넘기는" 과정을 하이드레이션이라고 해요. 코드로는 서버에서 prefetchInfiniteQuery로 첫 페이지를 가져와 dehydrate로 직렬화한 다음, HydrationBoundary로 클라이언트에 전달해요. 그러면 클라이언트는 첫 페이지를 다시 안 가져오고 바로 두 번째 페이지부터 요청하죠. 글이 말한 self-fetch 서버 컴포넌트와는 다른 방식인데, 글보다 못한 게 아니라 무한스크롤이라는 다른 문제를 푸는 거예요.

여기서 한 가지는 최근에 손봤어요. 검색 결과 페이지는 원래 이 하이드레이션을 페이지가 직접 했어요. 페이지 안에서 첫 페이지를 prefetch하고, 거기서 다음 페이지 주소랑 JSON-LD까지 계산해서 내려보냈죠. 그걸 SearchResultsData라는 별도 컴포넌트로 빼서 <Suspense>로 감쌌어요. 하이드레이션 방식 자체는 그대로예요. 데이터를 쥐는 자리만 페이지에서 컴포넌트 쪽으로 내린 거죠. 이제 검색 결과 페이지는 필터 껍데기랑 로딩 경계만 놓고, 결과 데이터는 그 컴포넌트가 안에서 가져와요. 무한스크롤이라 완전한 self-fetch로는 못 가지만, 앞에서 본 "페이지는 배치만" 쪽으로 이 트랙 안에서 한 발 더 간 셈이에요. (큐레이션 페이지는 아직 페이지가 직접 prefetch하는 예전 방식 그대로고요.)

로딩 처리는 라우트 성격에 맞춰 두 가지를 섞어요. Next에는 라우트 전체에 로딩 화면을 씌우는 loading.tsx라는 게 있어요. 검색 진입 화면들(/search, /search/results)처럼 서버에서 데이터를 받아 스트리밍하는 라우트엔 이걸 둬요. 클릭해서 넘어오는 순간 화면이 이전 페이지에 멈춰 있지 않고 바로 스켈레톤부터 뜨게 하려는 거예요. 반면 레시피 상세 하단 슬라이드처럼 한 화면 안에서 부분부분 채워지는 곳은 컴포넌트마다 <Suspense>를 걸어서, 어느 부분이 먼저 뜨고 어느 부분이 나중에 채워질지를 더 잘게 정하고요.

솔직하게 덜 된 곳도 있어요. 아까 홈 디스커버리 슬라이드 다섯 개가 자기 데이터를 직접 가져온다고 했잖아요(②는 지킴). 근데 이 슬라이드들은 상세 페이지와 달리 <Suspense>로 안 감싸져 있어요(④는 빠짐). <Suspense> 없이 두면, 그 슬라이드가 데이터를 다 가져올 때까지 페이지의 나머지 부분도 같이 기다려요. 상세에선 슬라이드마다 경계를 쳐서 먼저 뜬 것부터 보여주는데, 홈은 아직 그렇게 안 해놨어요. ②는 지켰는데 ④는 빠진, 반만 한 상태인 거죠.

좋은 구조는 의지가 아니라 강제가 만든다#

여기까지가 글과 우리 코드의 대조였어요. 이제 아까 미뤄둔 질문으로 돌아올게요. 이 구조가 좋은 건 알겠어요. 근데 무엇이 이걸 계속 지키게 만들까요?

새 팀원이 들어와서, 또는 내가 바쁜 날에, 그냥 페이지에서 await fetch 한 줄 박아버리면 어떻게 되죠? 아무도 안 막으면 원칙은 좋은 말로만 남고 코드는 슬금슬금 무너져요. 그래서 "안 지켰을 때 막아주는 장치"가 있어야 진짜로 지켜져요. 처음엔 답이 쉬울 줄 알았어요. 우리는 FSD에 린트까지 빡세게 거니까, 거기 룰 하나 추가하면 되겠지 했거든요. 알아보니 그게 아니었어요.

린트도 FSD도 이걸 막지 못한다#

먼저 린트. "페이지에서 데이터를 가져오면 에러" 같은 룰이 있나 찾아봤어요. 없어요. RSC용으로 제일 많이 쓰는 eslint-plugin-react-server-components가 하는 일은 "클라이언트 전용 기능을 쓰면서 "use client"를 안 붙인 파일"을 잡는 것뿐이에요. Next 공식 린트 플러그인도 이미지·스크립트·head 태그 관련 룰이 전부고요. "누가 데이터를 가져오느냐"를 보는 룰은 어디에도 없어요.

직접 만들면 안 되냐고요? 그게 어려워요. 린트는 코드의 글자 모양만 보지, 그 코드가 무슨 뜻인지는 몰라요. 페이지 안에 await가 보인다고 해서, 그게 데이터를 가져오는 건지 아니면 await params(주소 파라미터 읽기)처럼 무해한 건지 구분을 못 해요. 결국 함수 이름이 get으로 시작하면 잡는 식의, 이름만 보고 때려맞히는 룰밖에 안 나와요. 쉽게 깨지죠.

그럼 우리가 자랑하는 FSD는요? 이것도 못 막아요. 우리 eslint.config.mjs에 있는 fsd-import 룰을 열어보면, 검사하는 게 전부 import 문장의 경로예요. 예를 들어 아래 레이어인 shared가 위 레이어인 features를 import하면(의존이 거꾸로 된 거죠), 또는 같은 레이어끼리 서로 import하면 에러를 내요. 한마디로 "어느 파일이 어느 파일을 import해도 되는가"만 봐요.

await fetch() 같은 함수 호출은 이 룰의 관심 밖이에요. FSD가 보는 건 파일들 사이의 import 관계지, 코드가 실행될 때 누가 데이터를 가져오느냐가 아니거든요. 둘은 아예 다른 걸 보는 거라, fsd-import 룰을 아무리 조여도 page.tsx 안의 await getStaticrecipionServer()는 그냥 통과해요.

빌드를 실패시키는 단 하나 — Next 16 cacheComponents#

이걸 진짜로 막을 수 있는 건 Next 16의 cacheComponents라는 기능 하나였어요. 켜면 규칙이 하나 생겨요. 매 요청마다 바뀌는 데이터(캐시 안 된 데이터)를 <Suspense> 밖에서 가져오면 빌드가 실패해요. 에러 메시지도 대놓고 "Uncached data was accessed outside of <Suspense>"(캐시 안 된 데이터를 Suspense 밖에서 읽었다)예요. 개발 중에도 에러로 뜨고, CI에서 next build로 배포 빌드를 돌릴 때도 터져서 배포 자체를 막아요.

통과하려면 둘 중 하나를 해야 해요. 그 데이터가 매 요청마다 바뀌지 않으면(예: 며칠에 한 번 바뀌는 인기 목록) 함수에 'use cache'를 붙여 미리 만들어 두거나, 매 요청마다 바뀌면 <Suspense>로 감싸거나요.

이게 린트랑 결정적으로 달라요. 린트는 "이렇게 쓰는 게 좋아요" 하고 권할 뿐, 안 따라도 코드는 돌아가요. 반면 cacheComponents는 안 지키면 빌드 자체가 실패해서, 안 고치면 배포를 못 해요. 한 가지 짚어둘 건, 이게 "페이지는 fetch 금지"를 직접 강제하는 건 아니라는 거예요. 강제하는 규칙은 "매 요청마다 바뀌는 데이터를 읽으면 그 위에 <Suspense>가 있어야 한다"예요. 페이지가 데이터를 컴포넌트로 내려보내고 <Suspense>로 감싸게 되는 건, 이 규칙을 지키다 보면 자연스럽게 따라오는 결과고요.

왜 우리는 아직 안 쓰고, 지금은 무엇이 지키나#

그래서 우리는 켰냐. 못 켰어요. 두 가지 이유예요.

첫째, 우리는 Next 15.3이라 cacheComponents 기능 자체가 없어요. 16부터 들어온 기능이거든요. 둘째, 설령 16으로 올려도 바로 켜기가 어려워요. 우리 핵심 페이지 상당수가 방금 본 하이드레이션이나 서버 메타데이터 생성에 기대고 있는데, cacheComponents는 "Suspense 밖은 전부 미리 만들어 둔다"는 전제로 돌아가서, 이 둘을 맞추려면 페이지를 꽤 손봐야 하거든요.

그래서 솔직한 답은 이거예요. 지금 우리 코드에서 이 구조를 지키는 건 린트도 프레임워크도 아니에요. 그냥 컨벤션과 코드리뷰예요. 슬라이드를 만들 땐 자기 데이터를 직접 가져오게 짜던 습관, FSD 슬라이스 구조가 자연스럽게 만든 패턴, 그리고 PR에서 "이거 페이지에서 가져오지 말고 슬라이드 안으로 넣죠" 하고 한마디 거드는 것. 그게 전부예요. 나중에 16으로 올려서 cacheComponents를 켠다면, 메타데이터랑 안 엮인 곁다리 위젯(트렌딩이나 추천 같은)부터 <Suspense>로 감싸 적용해보는 게 첫 발이 될 것 같아요.

마무리 — 원칙과 제약이 만나는 선#

글을 다 대보고 나서 든 생각은, 우리 구조가 글의 이상을 베낀 것도 아니고 그렇다고 동떨어진 것도 아닌, 제약이 허락하는 만큼만 따라간 모양이라는 거였어요. 컴포넌트가 자기 데이터를 가져오는 핵심은 거의 다 따라갔고, 검색 노출 때문에 어쩔 수 없는 한 군데에서만 페이지가 데이터를 쥐고 있었죠.

남은 숙제는 두 개예요. 홈 슬라이드에 <Suspense> 경계를 마저 치는 것, 그리고 언젠가 16으로 올릴 때 곁다리 위젯부터 cacheComponents를 시험해보는 것. 강제 장치가 생기기 전까지, 이 구조는 결국 리뷰에서 한마디씩 거드는 걸로 버텨야겠죠.
